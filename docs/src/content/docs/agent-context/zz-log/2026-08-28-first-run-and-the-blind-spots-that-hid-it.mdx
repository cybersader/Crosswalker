## 1. Thirty seconds

**Crosswalker** imports compliance frameworks into an Obsidian vault as ordinary markdown notes and lets you link evidence to them. The goal driving the project is being usable for real work at an organization.

**What happened today:** the very first thing a new user does was broken, and had been for some time. Import a framework and the plugin would report, on the same screen and at the same moment, that it had created 12 notes and that nothing had been imported. Nothing was actually wrong with the import. The notes were correct and on disk. Everything that *looked* at them disagreed that they existed.

**The lesson, which is bigger than the bug:** it was found by a person opening an empty vault, not by any test. Every automated test and every screenshot taken that week started from a vault that already had content in it, so not one of them walked the only path a new user takes.

**What you need to do:** nothing. It is fixed, and the walkthrough is now a test. Section 7 lists what is still open.

---

## 2. Two minutes: what a new user actually saw

The default settings, the bundled NIST recipe, and an empty vault. That is the shortest possible path through the product, and it ended here:

| Surface | What it said |
|---|---|
| The import results screen | **Created 12 notes** |
| The workspace home screen | **Nothing imported yet** |
| The status bar | **no ontologies yet** |
| The coverage report command | Refused, with **Import a framework first** |

Four surfaces, one vault, two mutually exclusive answers. A person seeing this cannot tell whether the import worked, and the reasonable conclusion is that the product does not.

---

## 3. The cause: paths are guesses, not facts, for the third time

Installed frameworks were counted from **folder shape**. Discovery walked the output location and treated each subfolder as one installed framework, skipping loose files. There was a comment in the code saying that only folders count.

The bundled NIST recipe writes a **flat** layout. It puts notes directly into the configured output folder and creates no subfolder at all. So the default recipe and the default detector disagreed about what an import looks like, and the default settings put them in precisely the arrangement where they disagree. Nobody had to do anything unusual to hit this.

The fix is to stop asking the filesystem and start asking the notes. A note counts when its own provenance says Crosswalker produced it, and it joins the group named by its **CURIE prefix** (the short identifier namespace, such as `nist800-53`, that every generated note already carries). Path never participates. Flat and nested layouts now produce identical summaries because layout is no longer an input, and hand-authored folders stay out because they carry no provenance, which is a stronger exclusion than the folder-name check it replaces.

<Aside type="caution" title="Name the pattern: paths are guesses, not facts">
This is the **third** defect from inferring meaning from vault paths, and the third time it has been wrong.

1. **Re-import reconciliation** matched notes by where they lived, so a note that moved became a duplicate. Fixed by matching on identity. See [re-import is identity reconciliation](/crosswalker/agent-context/zz-log/2026-08-21-reimport-is-identity-reconciliation/).
2. **Orphan detection** had no reliable answer to "which notes did this import produce," and the destination folder was rejected as an ownership key for exactly this reason: it is a path, and [paths are guesses, not facts](/crosswalker/agent-context/zz-log/2026-08-21-import-set-ownership/). Fixed by minting an import-set id.
3. **Installed-framework discovery**, today.

The notes have always said what they are. The rule is to ask them. Any future code that reads a vault path in order to decide *what something means* should be treated as a defect report until proven otherwise. A path may be used to *find* candidates. It may not be used to *classify* them.
</Aside>

There was a second, independent failure on the same screen. The coverage report read the fast query index without refreshing it, so it saw whatever the one-time background pass at vault open had seen, which for a framework imported minutes after the vault opened is nothing. It now refreshes before reading, and reports the failure rather than an empty result if that refresh fails. Two unrelated bugs producing one symptom is part of why this looked, from the outside, like one confusing product rather than two fixable defects.

---

## 4. Why a week of green suites never saw it

This is the part worth carrying forward.

The suite was green. The screenshot runs were green. The static gates were green. A whole week of real-Obsidian E2E work had just landed, including a deliberate replacement of an 11,198-note dev-vault copy with a small purpose-built seed vault. And **every one of those runs started from a seeded vault**: a vault that already contained generated notes, arranged the way the tests expected.

A seeded vault is a good default. It makes runs fast and deterministic, and it is the right starting point for the great majority of assertions. But it silently encodes an assumption, *content already exists*, and that assumption is false for exactly one user: the new one. The empty-vault path was not undertested. It was **untested**, by every suite, with no gap visible anywhere, because a gap in coverage looks identical to coverage that passes.

`tests/e2e/first-run.spec.ts` now walks it: an empty vault, a real 12-row NIST 800-53 slice imported through the visible wizard, and then assertions that the contradiction cannot come back. The workspace names the framework, the status bar counts one, and the coverage command opens a report.

| Blind spot | What it looked like | What closed it |
|---|---|---|
| No suite crossed the empty-vault path | Green everywhere | An E2E spec that starts from an empty vault and imports through the real UI |
| Two pages describing first-day behavior were written from memory | Plausible prose | Both now carry a `Status last verified` marker citing the empty-vault run, not a reading of the source |

The two pages are [quick start](/crosswalker/getting-started/quick-start/) and the [command reference](/crosswalker/reference/commands/). The quick start walked a flow that ended at a screen saying nothing had been imported. The command reference listed names that no longer matched the palette. Both were verified against the product rather than against recollection, and the markers say so.

<Aside type="note" title="The generalizable rule">
Ask of any fixture: **what does this fixture assume that a real user does not?** A seeded vault assumes content exists. A vault with one framework assumes no cross-framework ambiguity. A run inside a single session assumes no restart. Each assumption is a path nothing tests, and none of them will ever show up as a failure.
</Aside>

### That question, asked of all 48 specs

Later the same day the rule above was turned on the suite itself, as a read-only audit. The question was not *which tests fail* but *what does each spec assume about the vault it starts in, and what could break without any of them noticing.* It found one assumption of exactly the shape that produced this morning's bug, and fifteen smaller ones.

**The matching one: the configured output folder is never written to, by any spec, at any point in the run.** The [purpose-built seed vault](/crosswalker/agent-context/zz-log/2026-08-24-e2e-testing-strategy-synthesis/) does not set the output path, so it keeps the shipped default `Ontologies/`. Every spec writes somewhere else — `Frameworks/`, `Crosswalks/`, `Evidence/`. Installed-framework discovery resolves only the configured output folder, so for the whole run it resolves an empty folder and renders the empty state. `first-run.spec.ts` is the only spec in the repository that names `Ontologies/` at all, and it is the one spec excluded from the shared configuration. The surface repaired this morning is therefore dark for all 48 remaining specs: discovery, the status-bar count, the import-again affordance and orphan scanning can all break with the suite fully green. This is the same "a gap in coverage looks identical to coverage that passes" that the first-run bug rode in on, still present, one layer over.

The other findings worth naming, ranked, with what each one hides:

| Finding | What it conceals |
|---|---|
| No spec ever opens a Tier 2 index written at an older schema version | A migration that throws on upgrade. Every existing vault fails to open its index after a plugin update, suite green |
| The SSSOM spec declares its own copy of the predicate map instead of importing the shipped one, and its fixture contains neither `broadMatch` nor `narrowMatch` | Re-inverting the exact mapping direction this project has already got wrong once, invisibly |
| Two sidecar tests assert the opposite of their titles: the "respects the configured path" test never changes the setting, and the "skips auto-projection when disabled" test only checks that manual projection still works | A hardcoded index path, and a startup scan that runs for someone who turned it off |
| `moved` and `orphans` are asserted by zero specs | Duplicate-instead-of-move, or every note reported as an orphan. Given that [path inference has now produced three defects](/crosswalker/agent-context/zz-log/2026-08-21-import-set-ownership/), this is the likeliest live one |
| `re-import.spec.ts` performs no re-import, and `full-import-flow.spec.ts` never asserts `result.success` or `result.errors` | An import that reports failure while still writing files, and the cache-lag frontmatter-wipe risk that the re-import spec's name implies is covered |
| Six specs are gated behind environment variables no runner sets, including everything proving real-corpus fidelity and the loudness contract for empty filtered imports | A source predicate regressing to a silent empty import, with zero coverage in any default run |
| Six specs contain no assertion at all, and a seventh stops asserting 60% of the way through, emitting the rest as console findings | Roughly twenty green declarations carrying near-zero evidence. Two of them navigate to paths that exist only in a retired vault |
| The four scale specs each clean `Frameworks` rather than their own destination | Nothing today, because they are gated off. The first person to enable them destroys the seed corpus and about fifteen other specs' output, and the failures will read as product regressions |

Four themes are structural rather than per-spec, in the sense that fixing any single file does not touch them: one shared mutable vault with no per-spec reset and no cleanup afterwards, so whole-vault assertions are ordering-coupled by construction; the unpopulated output root above; the assertion-free specs; and the env-gated specs nobody runs. The rest are one-to-five-line edits.

**The recommended first move was one fixture key, not a spec rewrite:** set the seed vault's output path to `Frameworks`, run the suite once, and read what turns red. It is reversible, it edits no test, and any spec that fails is by construction a spec that was passing only because the discovery surface was empty — which is the audit's finding, delivered as a failing test rather than as prose. The sidecar-migration gap is the largest remaining hole and is new-spec work; the SSSOM map, the two mistitled sidecar tests, the missing success assertion and the four scale-spec cleanups are small edits that should ride along with whatever commit follows.

### The one-key experiment, run

That key was added the same day and the suite was run twice, before and after, on an idle host. **The prediction above is now a measurement, and it was wrong in an interesting direction: the change turned almost nothing red, and what little it moved was worth more than the failure count suggests.**

| | Before | After |
|---|---|---|
| Spec files | 41 passed / 6 failed | 41 passed / 6 failed — *identical* |
| Declarations | 167 passed / 8 failed / 26 skipped | 166 passed / 9 failed / 26 skipped |

At spec-file granularity the two runs are indistinguishable, and the six failures are exactly the six visual specs already quarantined. One declaration moved from passing to failing. Nothing moved the other way.

**The value is not in the one new failure. It is in an assertion that kept its verdict and inverted its evidence.** `visual-workspace-flow.spec.ts` reads the workspace's installed-frameworks list after generating a framework and asserts the framework's name appears in it. Before the key, that assertion failed against an empty string: the list element was never rendered at all, because discovery resolved the configured `Ontologies/`, found nothing, and took its empty-state branch. After the key it fails against `NIST CSF 2.0 (CPRT export, nested)8 notes · 0 linksImport again` — a real row, with a real note count and a working import-again button, matched against the identifier form rather than the display title the interface renders.

That is the whole point of the exercise, and it is invisible in a pass/fail count. The assertion was failing for the reason that a feature did not run; it now fails for the reason that a feature runs and the expectation is written against the wrong string. **For the entire life of this suite, the installed-frameworks list and the status-bar count had never once produced a non-empty result under any spec.** The surface repaired that morning went from untested to tested by changing one line of fixture configuration, and no test was edited to get there.

<Aside type="caution" title="A vacuous assertion and a satisfied one look the same from the outside">
Both of these runs report the same failure on the same line of the same spec. Only the recorded string distinguishes "the feature never ran" from "the feature ran and my expectation is stale." A suite that stores verdicts and discards evidence cannot tell them apart, and neither can a reader of its summary.
</Aside>

### What it revealed in the product

The single new failure is not a fixture problem. It is a live defect, and it is the more valuable half of the result.

**Every import defaults its destination to the bare shared output folder, so a per-import folder rule that exists, is unit-tested, and was an explicit owner call never runs.** On 2026-07-11 the rule was set down that each import nests under its own folder inside the configured output path, because writing straight into the shared root flattened one import's top-level folders into everyone else's. The function implementing it was changed accordingly and is covered by passing unit tests. Its only caller in the wizard sits behind a guard that fires only when the destination is blank — and the wizard's constructor has already filled it with the configured output path, which ships non-empty. The guard cannot fire. The rule has never executed for any user who did not manually erase the setting.

The experiment surfaced it because it is only observable once the output folder has something in it:

| With defaults, a user | What happens |
|---|---|
| Imports their first framework | Lands in the shared root rather than its own folder. Nothing looks wrong yet |
| Imports a second, unrelated framework | The destination now holds one owned collection, so the wizard quietly preselects **refresh that collection**. Importing MITRE would stamp it with the identity of the earlier NIST import and report every NIST control as missing from the source |
| Imports a third | Two collections is ambiguous, so the wizard now requires a choice and refuses to advance. The requirement is announced only by a transient notice when the button is pressed |

Nothing is deleted — orphans are reported, never removed — so this is misattributed ownership and a spurious change list rather than data loss. It is still the ownership machinery firing correctly on an ambiguity that should never have been created.

The blocked-wizard case is what the new test failure actually is. That is a defect reaching a person through the shortest path in the product, found by a one-line fixture change, in a surface that six weeks of green runs never entered.

**A second instance of the same flattening is a question for the owner rather than a fix.** The recognized-recipe fast path also returns the bare configured root, discarding the curated per-framework folder the registry carries. Its comment says that is deliberate. But it was written four hours *before* the per-import-root rule on the same day, so it reads as a decision the later call superseded and nobody went back to reconcile. Which of the two governs is an owner call, not an inference — the runtime evidence is that a user on defaults sees the recognized-source card say their import "lands in Frameworks", the shared root, never the curated folder.

Two things the audit deliberately declined to call defects, because reading them as defects is how audits lose their credibility: the pure in-memory unit tests wearing an Obsidian costume are cheap, deterministic and honest about it, and the nine bodiless `it()` calls for an unlanded phase are the correct representation of work that has not happened.

### The defect, fixed the next day (recorded 2026-08-29)

**The guard was asking the wrong question, and that is the whole story.** It wanted to know one thing: *has the user chosen a destination?* What it actually asked was: *is the destination empty?* Those are the same question only in a world where nothing else may write to that field, and something else did — the constructor, fifteen hundred lines earlier, filling it with the configured output path before the user had seen a screen. One line seeded a value; another line read that value as an answer to a question about intent.

The fix does not make the guard smarter. It records the thing the guard was trying to infer. A flag is set when, and only when, the user edits the destination. The derived per-import root applies when that flag is false. Emptiness is never consulted again.

Three rulings rode along, all of them about not making the same class of mistake one layer over:

| Ruling | Why |
|---|---|
| The configured output path stays the **global root**; the per-import folder nests inside it | A user who customised that setting keeps it as the parent. The per-import rule adds a level, it does not relocate anyone |
| A **curated** folder for a recognised source beats a derived one, and both nest inside the global root | This closes the reconciliation section 4 called an owner call. The curated folder is a better per-import root than a filename-derived one, so it wins, but it does not get to escape the configured root. Crosswalk and junction recipes are the exception and keep their homes outside it, because they are not framework output and moving them would relocate the mapping and evidence surfaces that read them |
| **One accessor answers "where does this land"**, and every write path, preview, tree, breadcrumb and ownership check reads it | The old code derived the value inside a render method and wrote it back into the field it was reading. Two surfaces could disagree, and the field being read was also the field being mutated |

**Verified against a real run, not only against unit tests.** An import that had always written into the shared `Frameworks` folder now writes into `Frameworks/attack-mini`. `visual-workbench.spec.ts` had never once completed a generation in the life of that spec, reporting `NO_GENERATE` because the ownership question blocked the step before the generate button exists, and it now returns `created: 22, ok: true`. That is the blocked-wizard case from the table above, disappearing because the ambiguity that produced it is no longer created. The full end-to-end suite ended at 167 passing, 26 skipped, and 8 failures that are exactly the pre-existing quarantined visual specs: one net gain, no losses.

**What the fix deliberately does not do.** It never moves anything that already exists. A refresh keeps the destination its notes already use, except that nothing can currently look that up: an import set records its id and its identity scheme and **no destination at all**. The only way to answer "where does this set live" today is to read the paths of its notes, which is the exact inference this project has already banned three times. So the invariant holds by construction rather than by lookup. The derived root is a pure function of the output path and the source file name, so re-importing the same source resolves to the same folder and finds its own collection there.

That construction is sound for a vault created after the fix and hazardous for one created before it, and an adversarial review confirmed the shape of the hazard:

| Confirmed | What happens |
|---|---|
| An existing flat vault is not recognised | The next import resolves to the new per-source folder, finds nothing, and mints a new collection. On the default *skip* it splits one collection across two folders; on *replace* it moves every note into the new one. Nothing is deleted either way, and typing the old path keeps it |
| Home and grouping notes are matched by location, not identity | So a changed destination copies them rather than moving them. Duplicate names then make existing links to that name ambiguous. This is the one place the fix can produce a genuinely new duplicate, and it is confined to the first import after the change |
| Two renderings of one framework still share a folder | The curated folders are per framework, not per source layout, so the hierarchical and flat NIST CSF exports both land in `NIST CSF 2.0` and the second is offered as a refresh of the first. **The original defect, intact, in the recognised-source path**: narrowed from every import to a specific pair, but not gone |
| Switching source file after typing a destination keeps the destination | Which sends the second source into the folder belonging to the first: the same misattribution, reachable inside one session, in the file the fix lives in |

The first two are migration questions and the honest answer to both is the same: before generating, compare where this import will land against where the selected collection actually keeps its notes, and if they differ, *ask*. Not because asking is nice, but because "the destination moved" is currently indistinguishable from an ordinary run, and every one of these failures is a consequence of that indistinguishability. The third and fourth are small edits.

### The unblock attempt: written, tested, and still blocked (2026-08-29)

The migration hazard above was taken as the next piece of work, and given a **falsifiable bar rather than a checklist**. A vault holding a pre-fix flat import, refreshed after the fix, must show: zero duplicate identifiers, zero unsolicited moves of the user's existing notes, zero new orphans, no ambiguity error, and a results screen naming folders that actually exist — under **both** the *skip* and *replace* settings. Anything less and the fix stays blocked.

Seven decisions were frozen before implementation started, so that implementation could not quietly redesign the thing it was fixing:

| # | Frozen decision |
|---|---|
| 1 | A collection's destination is **recorded** when it is minted, and **recovered** for older collections as the folder prefix all its notes share, compared whole segment by whole segment. A string prefix would merge `NIST-mini` with `NIST-minimal`. An empty result or the vault root means refuse, not guess |
| 2 | Destination precedence, highest first: what the user typed, then the collection being refreshed, then the curated folder, then the derived one. Never adopt a root that would orphan or duplicate notes an existing collection already owns |
| 3 | Break the circularity — *you cannot ask where a collection lives without first naming a destination* — by identity, the way this codebase resolves everything else. Before defaulting the destination, look for a collection that already owns the identifiers this source will produce. Exactly one match adopts its root; several defer to the existing ambiguity path; none derives a new root |
| 4 | Home and grouping notes must not encode their folder in their identifier |
| 5 | Which changes those identifiers, so the old form must be recognised as an alias and reconciled, never orphaned. Whether that is even possible turns on a fact the implementation had to settle first: can such a note hold writing a person put there? |
| 6 | Home and grouping notes reconcile through the identity index, like every other note |
| 7 | A not-yet-indexed file means *not indexed yet*, never *absent* — the same raw-read fallback the ownership scan had already grown for exactly this reason |

All seven were implemented. Decision 5 resolved to the harder branch: those notes **do** carry user prose and user-preserved keys, through a merge path with no conflict return, so regenerating them at the new address would destroy writing. Aliasing was the only available answer.

The evidence behind them is not thin. The unit suite is green at 2,143 tests, including a new spec that builds a genuinely pre-fix vault by generating with the *current* engine and then de-migrating it, so it cannot pass by seeding a shape the engine would never produce. Every one of those tests was then **falsified**: each frozen decision was reverted in turn and the tests claiming to cover it were re-run, and no experiment came back empty. The end-to-end suite is unchanged against a corrected baseline, with **no declaration moving in either direction**, and it confirms the recorded destination landing in a real vault rather than only in a mock.

And the criterion is still not met.

**Under *replace* it passes. Under *skip* it fails, deterministically.** Under that setting every row returns before the enrichment records are collected, so the enrichment phase never runs at all: no home or grouping note is reconciled, none is restamped, and every one the collection owns is reported as gone. That was pinned as independent of this work, since the same phantom orphans appear on a vault the current engine generated moments earlier, with the setting as the only variable. It is marked in the suite as a known failure that will turn the suite **red** if it is ever fixed and the marker is not removed, rather than deleted or softened.

An adversarial pass then found more, seven of nine confirmed by trace:

| Found | Why it blocks |
|---|---|
| **Home and grouping notes move under *skip*** | The enrichment phase is never told which setting is in force. Its options carry three fields and that is not one of them. Ordinary note moves are explicitly gated on it; these are not. A person selects the setting whose entire contract is *leave my notes alone*, and their grouping notes are renamed |
| **The results screen names folders that do not exist** | Pre-existing and live today, independent of all of this. When a note is found by identity somewhere else and the move is suppressed, the skipped list is filled with the address the note *would* have had rather than the one it has. It does not arise in the tested scenario only because decision 3 holds the destination still. It arises everywhere decision 3 declines |
| **Nothing reports moves or orphans to a person** | Both are recorded in the result and read by no code anywhere in the plugin. Two of the five clauses in the bar are, today, **unobservable through the interface**: a test can check them and a user cannot. "Verified in a real vault" is not currently something a person is able to do |
| **The alias covers a changed rule, not a changed folder** | The old identifier is reconstructed from *this* run's folder, so it matches only while the destination stands still. The whole criterion therefore rests on decision 3 never declining, and it declines on a streamed source, a source above the probe limit, a cold cache, several claiming collections, or notes with no shared root |
| **Removing the folder from the identifier created a new collision** | Two imports of one framework into two folders now claim the same grouping identifiers. The second silently takes the first's notes; the next refresh of the first takes them back. Where both already exist it reproduces the original ambiguity error from an entirely new cause |
| **Recovery guesses where it was told to refuse** | The deepest folder every note shares is the import root only when something is actually written at that root. With a single-branch hierarchy, or a layout that opens with a fixed folder, it returns a folder several levels too deep, and every note in the collection is then relocated to match. The refusal rule covers the empty case and the vault root; it does not cover this one |
| **The cache fallback landed on one read path and the new lookup uses the other** | So on a cold cache the recovered root is computed from a *subset* of the collection, and a subset shares a deeper prefix than the whole. The over-deep case again, arriving by a second route, with nothing left to make it decline |

**The status is therefore: written, tested, honestly measured, and not shippable.**

Two of these are small and deterministic: tell the enrichment phase which setting is in force, and report the address a skipped note actually has. The rest turn on one unresolved question, which is the next *decision* rather than the next patch.

> **May a grouping note's identity be independent of the folder it sits in?**

Taking the folder out of the identifier is what makes the identifier survive a move. It is also what makes two folders collide. Half of that question was answered and half was not, and answering only half is what produced the last four rows of the table.

The answer proposed in the paragraph immediately above this subsection — before generating, compare where this import will land against where the selected collection actually keeps its notes, and *ask* — is still the answer. This attempt tried to turn that question into a lookup. The lookup is correct for a vault created after the fix, and still a guess for the vault that needs it.

<Aside type="caution" title="Name the pattern: identity must never be derived from address">
This is the **fifth** time, and the first four are already written down on this page and its neighbours. They look like five different bugs. They are one bug.

| # | The code observed | And concluded |
|---|---|---|
| 1 | A note folder | That is which import owns it — **path-based reconciliation**. See [re-import reconciliation](/crosswalker/agent-context/zz-log/2026-08-21-reimport-is-identity-reconciliation/) |
| 2 | A destination path | That is the ownership boundary — **path-based ownership**. See [import-set ownership](/crosswalker/agent-context/zz-log/2026-08-21-import-set-ownership/), where *paths are guesses, not facts* was first written down |
| 3 | A subfolder | That is one installed framework — **path-based discovery**. Section 3 above |
| 4 | An empty text field | The user has not chosen a destination — a guard asking whether a value was **empty** when it meant to ask whether a person had **chosen**. Section 4 above |
| 5 | The folder a grouping note sits in | That is **part of what the note is**, written into its identifier. So moving the folder changed the note's identity, and the note orphaned itself. Section 4, the unblock attempt |

Instance 5 is the deepest of the five, and the reason the fix above is still blocked. The first four read an address and drew a conclusion *about* a note. The fifth put the address **inside** the note's identity, so no amount of reconciling downstream can help: the thing being matched changes whenever the folder does. Every layer above it — reconciliation, ownership, orphan reporting, the destination default — was repaired on the assumption that identity holds still. Under it, one identity did not.

The absence-read-as-fine family is the same shape said the other way round: a missing cache entry read as *no result* ([closure cache](/crosswalker/agent-context/zz-log/2026-08-20-closure-cache-fix-and-what-it-means/)), a not-yet-indexed file read as *no frontmatter*, a delete that found nothing read as *already clean* (section 5). In every case the code looked at a value it was allowed to see and reported a fact it had not established.

**The rule, stated once for all five:** when you need a fact about **identity or intent**, record it at the moment it is true and read it back. Never reconstruct it from a value that some other line of code is allowed to write. A path may be used to *find* candidates and never to *classify* them; an empty field means the field is empty, never that a person declined to fill it; and **an identifier that contains an address is not an identifier** — it is an address wearing one, and it will change the day the address does.

**The corollary, learned the hard way this time:** taking an address *out* of an identifier is not free. An identifier that included the folder was, accidentally, also unique per folder. Removing the folder makes the identifier survive a move and makes two folders collide, and both halves have to be answered in the same change. Answering only the first half is what left this fix blocked.

The tell is grammatical. Every one of these is a condition whose expression and whose purpose are about different things: `if (!outputPath)` standing in for *the user has not chosen*, a folder-shape walk standing in for *this is a framework*. When the question in the comment and the question in the expression are not the same question, that is the bug, and it will survive every test written by anyone who read the comment.
</Aside>

### The second attempt: the right rule, and four clauses it still does not clear (2026-08-30)

The attempt above was blocked on a question it could not answer. This one reframed the question instead, and **the reframing is the durable result of the day**, even though the code that came with it is still not shippable.

#### The reframing

**Both blocked passes were solving relocation.** Each asked the same thing: *the destination changed, so find where these notes used to live and either move them or teach the new address to answer to the old one.* Answering that requires knowing the old folder, which is the very fact the recovery was trying to establish. So every mitigation ended up resting on a guess that was allowed to decline, and each decline reopened one of the clauses. That is why the previous table has seven rows and four of them are the same shape.

**The rule that deletes the question: a refresh never changes where a collection lives.** The destination for a refresh *is* the collection's existing folder, read once from the notes it already owns and then recorded so it is never worked out again. A brand-new collection gets its own derived folder, and a brand-new collection owns no existing notes, so a refresh has nothing to move and nothing to leave behind. Under this rule the relocation problem is not solved. It is **absent**.

This is the page's own rule applied one level up. *Identity, never path* has been written down five times here and on its neighbours, and every time it was about a note. A collection's folder is the same kind of fact: not something to infer from where its notes happen to sit, but a **property of the collection**, which is already identified by a recorded identifier. Once the folder is a recorded property, there is nothing left to infer, and nothing left for a heuristic to decline.

**Moving a framework to a different folder does not disappear; it becomes something a person asks for**, with its own confirmation and its own summary of what moved. That is also the honest migration path for a vault whose imports all sit in one shared folder: not a rule that quietly rearranges notes on the next refresh, but an operation the owner of the vault chooses and watches. It is purely additive — nothing in this attempt has to change to add it, and it belongs on the [v0.1 milestone track](/crosswalker/reference/roadmap/milestones/) as its own piece of work — and it is the reason building the "what moved" reporting *before* anything can move was worth doing.

#### What was built

| Rule | What it does |
|---|---|
| The destination of a refresh is the collection's own folder | Shown read-only, as *Refreshing into `<folder>`*. Editing it during a refresh would be a relocation request, so the field is not offered |
| Ownership is decided from the whole vault, by what the notes are stamped with | Replaces the old rule, which looked only inside the destination folder and preselected *refresh* for whichever single collection happened to be sitting there, whatever it was. That rule was the misattribution bug |
| A collection with no recorded folder recovers one, whole folder name by whole folder name | So `NIST-mini` can never merge with `NIST-minimal`. If the notes are spread across unrelated folders, it **refuses** and says so, rather than picking one |
| Nothing decides ownership while the vault is still being indexed | A not-yet-indexed file means *not indexed yet*, never *absent*. On a cold cache the wizard waits, then blocks with a message, and never generates |
| Grouping notes reconcile by identity, and the old form of their identifier is still recognised | Unchanged from the previous attempt, and now sound rather than conditional: the folder cannot change, so the old identifier is always reconstructed against the folder it was written under |
| A suppressed move reports the folder the note **is** in, never the one it would have gone to | And the enrichment phase is finally told which overwrite setting is in force, so grouping notes stop moving under *skip*. These are the two small deterministic findings from the previous attempt, both closed |
| Moves and orphans are shown to a person | Both were recorded by the engine and read by no code anywhere in the plugin. Two clauses of the bar were unobservable through the interface; a count line each now renders, expandable to the list |

**The evidence is not thin.** The unit suite is green at 2,174 tests across 117 suites, including a rewritten specification for the removed guesswork and a new one pinning the whole-vault ownership scan. Fourteen mutations were run: each rule was neutralised in turn and the tests claiming to cover it re-run, and every one isolated. The end-to-end suite shows **no declaration moving in either direction** — the eight residual failures are byte-identical to the baseline and all already quarantined — and a screenshot from that run shows the new behaviour live, with two collections found elsewhere in the vault and the import correctly defaulting to a new one.

#### And the criterion is still not met

Four clauses fail, independently. Two are carried forward and two are new.

| Found | Why it blocks |
|---|---|
| The ordinary wizard labels every import with the same placeholder | **Closed 2026-08-30. The class it belongs to is not.** The ordinary path now labels an import with the name of the file it came from, and matching ignores the placeholder labels. A second unrelated framework through that path now defaults to a new collection, falsified against the previous behaviour. The three rows below are the same defect through labels that are not placeholders |
| **Under *skip*, every grouping note the collection owns is still reported as gone** | Unchanged from the previous attempt and pinned as a known failure that will turn the suite red if it is ever fixed and the marker is not removed. Every existing row returns before the enrichment records are collected, so the enrichment phase never runs, no grouping note is restamped, and each one falls out of the "still present" set. Independent of the destination rule: it reproduces on a vault the current engine generated moments earlier, with the setting as the only variable |
| **The summary screen is drawn only on the runs that do not need it** | The "Moved: 0 notes" line was deliberately made unconditional, because a person who cannot see the zero cannot tell *nothing moved* from *nobody checked*. But the screen carrying it renders only when something moved or something orphaned. A clean refresh does neither, so the window simply closes. The orphan count is gated the same way one level down, so a zero is invisible even when the screen does appear. The clause asks for exactly the numbers the interface withholds |
| **A genuine ambiguity error ends the run on the success path** | **Closed 2026-08-30.** Any recorded error now forces the summary screen open with the collision named on it, and the finish message points at it. The rule is that a run which closes must show its errors. It is not yet applied to the mapping-import surface, or to a run whose only anomaly is a conflict; both are separate rows below |

Three smaller findings sit behind those, and are recorded rather than fixed:

- **The indexing precondition can report success without having run.** If a check is already in flight, a forced call returns *passed* whenever nothing has been refused yet — which is exactly the state during the bounded wait it exists to enforce. And it guards one door of four: the mapping-import surface and the bundled-fixture command never run it, and the mapping surface still uses the old folder-scoped ownership rule this change replaced.
- **Recovery still returns the deepest folder every note shares**, which is the collection's folder only if something is actually written at that folder. The classic path emits no grouping notes at all, so a collection whose notes all sit one level deeper recovers a folder one level too deep, and under *replace* every note is relocated to match. Carried from the previous attempt; the refusal rule covers the empty case and the vault root, and still not this one.
- **On the default path, neither the destination nor the ownership review appears until the final screen.** The write itself is correct — the final screen re-checks before generating — but the two clauses about what a person is shown *before* deciding are not met where most people will look.

**The status is therefore: reframed correctly, written, tested, honestly measured, and not shippable.** The reframing stands on its own and should survive whatever the code does next. The first row of the table above is the thing to fix first, because it is the original defect wearing the new fix's clothes.

### The third attempt: four clauses closed, six more of the same shape found (2026-08-30)

The second attempt named four failing clauses. This attempt fixed all four, and an adversarial pass over the result found six more failures of the same bar. **The four fixes are correct and should survive. The bar is still not met**, because the class of defect they were aimed at is wider than the four instances that had been found.

#### The three rules the fixes generalize into

The four amendments were written as separate items. They are one rule each, and each is worth more than the fix it produced.

| Rule | What it replaces |
|---|---|
| **A refresh never changes where a collection lives** | Guessing the old folder in order to move notes into a new one. Carried unchanged from the second attempt, and still the load-bearing idea |
| **A placeholder is never an identity** | Treating a filled-in default as a fact about the thing. The ordinary wizard stamped every import with the same two placeholder labels, and the matching rule then paired every import with every other |
| **A run that closes must show its errors** | Reporting success and closing the window over a recorded failure. The same family as the reset that reset nothing, one screen up |

#### What was built, and how it was measured

| Fix | What a person sees |
|---|---|
| The ordinary wizard labels an import with the name of the file it came from, and the matching rule ignores the placeholder labels entirely | A second, unrelated framework imported through the ordinary wizard now defaults to a **new** collection instead of being offered as a refresh of the first |

**The evidence is again not thin.** 2,200 unit tests green, 26 of them new and written to the four rules; eleven mutations run, each neutralising one rule in turn, and every one turned its own tests red while the baseline stayed green. #### And the criterion is still not met

Six findings, each independently defeating a named clause. Four of them are the *same* defect the whole change exists to end, arriving through a door the fix did not cover.

| Found | Why it blocks |
|---|---|
| **Several bundled imports share one label** | **Closed 2026-08-30 on the ordinary wizard, by removing the match rather than fixing the labels.** They still share labels. A shared label can now only draw a suggestion, and only when exactly one collection carries it, so two unrelated mapping imports land as two collections with nobody clicking anything. The guess it defeated survives on the mapping-import window, which is where the general-purpose mapping recipe actually runs — see the row below |
| **A saved configuration reused across two frameworks does the same** | The identifier of an applied saved configuration is stamped as the import's recipe identity. It is not a placeholder, so the new exclusion never fires. The ownership rules already say in as many words that a recipe identifier names reusable instructions and not ownership, and the matching rule promotes it to ownership anyway |
| **Two source files with the same name still collide** | **Closed 2026-08-30 for ownership, open for foldering.** Two exports both called `controls.csv` no longer resolve to one collection, because the name no longer decides anything. The destination folder is still derived from the file name, so the two still land in one folder unless a destination is typed. That half is the row on renaming a source, below |
| **There is now no way to refresh a collection imported before this change** | Making old imports never auto-match is the safe half. But every refresh control in the interface is drawn from the *matches*, and a collection that matches nothing produces none: no dropdown, no "refresh that one instead" button. The only offer is a new collection, which silently writes a second copy of the framework. The amendment's own text says the user can still choose refresh explicitly. There is no such control |
| **Explicitly refreshing such a collection reports every note in it as missing** | **Closed 2026-08-30 by the pinned label.** The refresh mints under the label the notes already carry, so the owned set and the produced set are the same set again, and nothing is restamped |
| **"No orphans" is still printed when nothing was checked** | The count that was made unconditional is read from a field the engine leaves unset in two different situations: *checked, found none* and *never checked*. If the step that finds missing notes fails, the failure goes to a warnings channel the wizard displays nowhere, and the finish message says "No orphans." anyway. That is precisely the distinction the amendment was written to make visible |

Two smaller findings sit behind those:

- **A "notes left unchanged" run still closes over its own screen.** That warning tells you to see the summary screen, and the summary screen is not drawn for it, although the screen has a section built for exactly that list. Errors were added to the condition that opens it; conflicts were not.
- **The mapping-import window prints `[object Object]` where the error should be**, and the branch meant to report a partial success on that path is unreachable. It is the only other import surface, and it swallows the same collision the wizard now shows.

#### The one thing that closes most of it

Five of the six reduce to a single omission: **a collection's label is not pinned.** When a collection is first created, its identifier scheme is fixed and a later refresh may not change it. Its label is not treated the same way, so it is re-derived from the source on every run and can quietly differ from the one on disk.

Pinning it at creation would make the misreported-refresh finding structurally impossible, make refreshing a pre-existing collection legitimate and therefore offerable, and turn the three auto-match findings from *the wrong collection is silently chosen* into *nothing matched, so make a new one* — which is the safe direction. That is an owner's call about the data model, not an implementer's, and it is the question to answer before a fourth attempt.

<Aside type="caution" title="Name the pattern: a placeholder is never an identity">
This attempt removed two literal placeholders and the defect walked straight back in through a label that looks like a real name. `xwalk` is not a filled-in default. It is the name of a *shape* — "this is a crosswalk" — doing duty as the name of a *thing*.

The test is not whether a value looks like a placeholder. It is whether **two unrelated things can end up carrying it**. If they can, it cannot decide ownership, no matter how meaningful it reads.

That is the same sentence as *paths are guesses, not facts* in section 3, one level over: a path is shared by everything in a folder, a shape label is shared by everything of that shape, and neither is an identity. The project's rule has been *identity, never path*. It is really **identity, never anything derivable**.
</Aside>

**The status is therefore: three good rules, four correct fixes, and a bar that is still not met.** The reframing from the second attempt and the two new rules from this one are the durable output. The branch is not shippable, and the next move is the owner's decision on pinning a collection's label, not another implementation pass.

### The fourth attempt: the guess deleted, and three doors it was never behind (2026-08-30)

The third attempt ended by naming one owner's decision: **pin a collection's label when the collection is created.** That decision was taken, and with it went the thing underneath all four attempts. The rule that a source can be matched to the collection it belongs to was not sharpened again. It was **removed**, and matching demoted from a decision to a suggestion.

That is the right move, it is implemented, and the acceptance bar is still not met — this time for a reason none of the previous three passes had reached. The guess was deleted from the ordinary wizard. It was never only there.

#### What was built

| Fix | What a person sees |
|---|---|
| Nothing preselects a refresh, anywhere in the ordinary wizard | The ownership step now lists **every** collection in the vault with its folder, how many notes it holds, and what produced it. The first and default choice is *import as a new collection*. A refresh happens only because someone picked one from that list |
| Matching became a suggestion | When exactly one collection carries the same label as the source, one line appears: *"Looks like `nist-csf-2`. Refresh it instead?"* One button. No match, or several, and there is no line. It suggests; it never decides |

| The mapping-import window shows its errors | It printed `[object Object]`. It now names each error, keeps the window open on a run that failed, and lists them on a screen |

Two of the third attempt's blocking rows close as a consequence rather than by a separate fix, which is the sign the rule was the right one. A collection imported before this change is now **listed**, so it can be refreshed — the control the third attempt removed and assumed was still there. The ownership tests went from 82 to 113, four more cover the mapping window, and eighteen mutations were run against them: each one restores a specific guess or drops a specific rule, and seventeen turned their own tests red. Three of those kills are the escape routes the third attempt found, now asserted directly: two crosswalks sharing the general-purpose label, one saved configuration applied to two frameworks, and two exports both called `controls.csv`. They were widened and re-checked on their own; the whole suite has not been run again since.

#### And the criterion is still not met

The bar's last clause is *a second unrelated framework, **any path**, with **no click**, lands in its own folder as a new collection, because nothing else is possible*. Four ways it is still possible.

| Found | Why it blocks |
|---|---|
| **The mapping-import window still guesses, and its default is to overwrite** | It is the surface the general-purpose crosswalk recipe uses for **every** pair of frameworks. If one collection already sits in the folder for that pair, it is adopted silently: no control on the screen, no click, and that window writes in *replace* mode, so the earlier crosswalk is rewritten in place and the rows it no longer covers become missing notes nothing there reports. This is the deleted code, alive one window over. The folder for a pair of frameworks is deterministic; who owns what is inside it is not, and that distinction is the entire argument |
| **"Not looked yet" is read as "nothing there"** | The wizard's own defence is a list that reads the same when the vault holds no collections and when the scan has not finished. Two ways into the later steps do not wait for the scan — a recognised source, and resuming a saved draft, which can resume directly onto the button that starts the import — and that button does not check either. In that window the ownership step draws **no control at all**, so there is nothing to click, and the import falls through to the older rule underneath, which adopts whichever collection happens to share the folder. It is timing-gated; the missing check is not. This is *cache lag is not absence*, reproduced inside the code written to stop inferring |
| **The bundled-example command has no ownership control at all** | It imports a sample mapping with no way to say where it belongs, so it adopts whatever is already there. It also ends by reporting *how many* errors occurred and none of them, which is the one rule this pass applied everywhere else. Developer tooling, and the bar says any path |
| **Two collections can claim one grouping note, and the write crosses the boundary** | The general-purpose crosswalk recipe creates one top-level grouping note per label, and the index deciding where a note goes is vault-wide rather than scoped to the collection doing the writing. So a second crosswalk under the shared label does everything right — it lands as its own new collection, with no click, exactly as the bar requires — and **still** renames the first crosswalk's top note into its own folder, leaving the first without one and reporting the move on its own screen. Pinned as a deliberately failing test rather than deleted, so the gap stays visible while the suite stays green |

One smaller finding sits behind them: the mapping window still has one exit, on an unreadable source file, that reports through the same truncating notice the rest of that window stopped using.

<Aside type="caution" title="Name the pattern: ownership cannot be derived, and deleting one derivation is not deleting the rule">
Four attempts guessed which collection a source belongs to. By the folder it was going into. By a label, with the obvious placeholders excluded. By a label, with the matching sharpened. Every one had an escape route, and each escape route was found only after the fix was written and tested.

The fourth stopped guessing, and the bar still failed. Two things were learned that the first three could not have shown.

**A guess is not a place in the code.** It was the product's ownership rule, and it is implemented on every surface that imports anything. Removing it from the surface where it was found removed one instance of it. The mapping window and the bundled command were never in scope of any of the four passes because nobody had looked at them, and one of them is where the label collision that defeated the third attempt actually lives.

**Ownership is not the only way a write crosses a boundary.** A collection can be entirely right about who it is and still be written into, because the index that decides where a note goes has never been scoped to the collection doing the writing. That is an identity question, not an ownership-default question, and it is untouched by all four attempts.

The project's rule was *identity, never path*, then *identity, never anything derivable*. The fourth attempt adds the part about where to apply it: **not on the screen where the defect was reported. On every surface that writes.**
</Aside>

**The status is therefore: the right rule, implemented, unverified, and three surfaces short.** Pinning the label was the correct owner call and it closed two blocking rows on its own. What remains splits cleanly in two, and only the second is a decision. Applying the same ownership rule to the mapping window and the bundled command is mechanical and already specified by what the wizard now does. Scoping the index that places a note to the collection being written — or refusing outright a move whose source belongs to another collection — is a data-model call and the question to answer before a fifth attempt. Neither is worth starting before the branch has been through an end-to-end run, because nothing in this pass has had one.

## 5. The same family, one layer down: a reset that reset nothing

Also on 2026-08-28, and the reason this log covers three things rather than one.

**Maintenance: reset search data** exists to throw away Crosswalker's derived search data so it can be rebuilt from the canonical notes. It was deleting nothing at all. The index is opened through one storage mechanism and the delete was attempted through a different one, behind a `typeof` guard that was never true. The guard was false, the function returned having done nothing, and the command still showed **Fast query index cleared**.

Every row the reset was supposed to destroy survived, and the next query answered out of it. Nothing downstream ever complained, because losing this data is safe by design. The index rebuilds from the notes, so an index that was never cleared behaves almost exactly like one that was cleared and immediately rebuilt. The one observable difference is *stale rows*, and only if you go looking.

The reset now deletes where the file actually lives, removes any partial write left beside it, closes the live connection first, then **re-reads and throws if anything survived**, so the command reports failure instead of a success it cannot see. The message now distinguishes three genuinely different outcomes: something was deleted, there was nothing to delete, or the data was only ever held in memory this session.

**The E2E test that covered this command is worth reading as an artifact.** It projected rows first, with a comment saying *"so we have data to verify is gone after clear"*, and then never checked that the data was gone. It asserted that the handle was null and that a later reprojection succeeded, with a further comment excusing the row counts as possibly zero. The test watched the mechanism and not the outcome, so it passed for months over a command that did nothing.

This is the same family as the [closure cache fix](/crosswalker/agent-context/zz-log/2026-08-20-closure-cache-fix-and-what-it-means/) and the [cache-lag bugs](/crosswalker/agent-context/zz-log/2026-08-21-import-set-ownership/): **absence read as fine**. A missing cache entry read as "no result." A not-yet-indexed file read as "no frontmatter." A delete that found nothing read as "already clean." In each case the code observed nothing and concluded that everything was in order, when the correct conclusion was *I cannot tell*.

It had also been flagged. [Challenge 45](/crosswalker/agent-context/zz-research/2026-08-19-challenge-45-org-rollout-readiness/) named the purge boundary as unproven, noted that the clear was best-effort and silently did nothing when the function was unavailable, and told pilots not to treat the index as a confidentiality boundary. The finding was recorded and correct. It took until today to become a fix.

| The destination defect the experiment revealed | **Fixed 2026-08-29, verified, with named residual risk.** The guard now reads a recorded choice instead of an empty field, the recognised-recipe reconciliation is decided (curated folder wins, nested inside the configured root), and a real run confirms the per-import folder. The residual items below are what the adversarial review found; delivery detail is in `CHANGELOG.md` `[Unreleased]`. **The follow-up making it safe for an existing vault did not clear its bar and is not shippable** — see the next row and section 4 |
| A vault that already imported into the shared folder | **Attempted four times, still open, and still the largest remaining item.** Its next import lands in the new per-import folder, does not recognise the earlier collection, and mints a new one: split on *skip*, moved on *replace*, deleted in neither. Two of the three rules under it are now settled — a refresh never changes a collection's folder, and a collection's label is pinned when it is created. What blocks it is no longer the rule but its reach: the ownership rule was applied to the surface where the defect was reported and not to the two other surfaces that import, and a write can still cross a collection boundary by identity even when ownership is answered correctly. See the four rows below and section 4 |
| The ordinary wizard labels every import with the same placeholder | **Closed 2026-08-30. The class it belongs to is not.** The ordinary path now labels an import with the name of the file it came from, and matching ignores the placeholder labels. A second unrelated framework through that path now defaults to a new collection, falsified against the previous behaviour. The three rows below are the same defect through labels that are not placeholders |
| **A genuine ambiguity error ends the run on the success path** | **Closed 2026-08-30.** Any recorded error now forces the summary screen open with the collision named on it, and the finish message points at it. The rule is that a run which closes must show its errors. It is not yet applied to the mapping-import surface, or to a run whose only anomaly is a conflict; both are separate rows below |
| **The indexing precondition can report success without having run** | **Open, and now the smaller half of the row below it.** A forced check that finds one already in flight returns *passed* whenever nothing has been refused yet, which is the state during the wait it exists to enforce. It also guards one entry point of four |
| **The mapping-import window still guesses ownership, and its default is to overwrite** | **New, blocking, and the same defect the ordinary wizard just stopped doing.** It is the surface the general-purpose mapping recipe uses for every pair of frameworks. If one collection already sits in the folder for that pair it is adopted silently, with no control on the screen and no click, and that window writes in *replace* mode, so an earlier mapping is rewritten in place and the rows it no longer covers become missing notes nothing there reports. The folder for a pair of frameworks is deterministic; who owns what is inside it is not |
| **A scan that has not started reads the same as a scan that found nothing** | **New, blocking.** The list the wizard defends itself with is empty both when the vault holds no collections and when the scan has not finished. Two ways into the later steps do not wait for it, a recognised source and a resumed draft, and the button that starts the import does not check. In that window the ownership step draws no control at all, so there is nothing to click, and the import falls through to the older rule underneath, which adopts whichever collection shares the folder. Timing-gated; the missing check is not. The same shape as reading an unfinished index as an empty one |
| **The bundled-example command has no ownership control at all** | **New.** It imports a sample mapping with no way to say where it belongs, so it adopts whatever is already there, and it ends by reporting how many errors occurred and none of them. Developer tooling, and the bar says any path |
| **A grouping note can be claimed by two collections, and the write crosses the boundary** | **New, blocking, and the next owner decision.** The general-purpose mapping recipe creates one top-level grouping note per label, and the index deciding where a note goes is vault-wide rather than scoped to the collection doing the writing. A second mapping import under the shared label therefore does everything the bar asks — its own collection, no click — and still renames the first one's top note into its own folder, leaving the first without one. Either those identifiers are qualified by the collection, or a move whose source belongs to another collection is refused. Pinned as a deliberately failing test so it stays visible while the suite stays green |
| **The branch has had no end-to-end run since the ownership rule changed** | **New.** The fourth attempt was not run end to end at all: the host was carrying an unrelated foreground workload at three times the pressure threshold with 7 GB swapped, and starting 47 headed sessions on top of that is the arrangement that locked the machine on 2026-08-21. Refusing was correct. A static pass in its place found that no end-to-end test touches any of the four changes, so the run is a precondition for shipping and not a source of confidence about them. The unit suite has also not been re-run green as a whole since three stale assertions were widened |
| **A collection's label is not pinned when the collection is created** | **Closed 2026-08-30, and it was the right call.** The label is stamped when the collection is created and a refresh mints under the collection's own label. A collection created before this change is pinned on its first refresh to whatever its notes already carry. Two blocking rows below closed as a consequence rather than by a separate fix. Residual: a collection whose notes carry two or more labels pins nothing and keeps the old behaviour, which is reachable in exactly the vaults damaged by the original defect |
| **Several bundled imports share one label** | **Closed 2026-08-30 on the ordinary wizard, by removing the match rather than fixing the labels.** They still share labels. A shared label can now only draw a suggestion, and only when exactly one collection carries it, so two unrelated mapping imports land as two collections with nobody clicking anything. The guess it defeated survives on the mapping-import window, which is where the general-purpose mapping recipe actually runs — see the row below |
| **A saved configuration reused across two frameworks is read as ownership** | **Closed 2026-08-30.** Nothing derived from the source decides ownership on the ordinary wizard any more, so a configuration identifier cannot promote itself to one. Falsified against the previous behaviour: one saved configuration applied to two frameworks now produces two collections |
| **Two source files with the same name still collide** | **Closed 2026-08-30 for ownership, open for foldering.** Two exports both called `controls.csv` no longer resolve to one collection, because the name no longer decides anything. The destination folder is still derived from the file name, so the two still land in one folder unless a destination is typed. That half is the row on renaming a source, below |
| **A collection imported before this change can no longer be refreshed at all** | **Closed 2026-08-30.** The ownership step lists every collection in the vault rather than only the matches, each with its folder, note count, and source, so a collection that matches nothing is still there to pick. The control the previous fix assumed was present now exists |
| **Explicitly refreshing such a collection reports every note in it as missing** | **Closed 2026-08-30 by the pinned label.** The refresh mints under the label the notes already carry, so the owned set and the produced set are the same set again, and nothing is restamped |
| **"No orphans" is printed when nothing was checked** | **Closed 2026-08-30.** Whether the check ran is now recorded separately from what it found, set to *not run* before the work starts so a failure part-way cannot read as *checked*. The finish message says *orphans not checked* and forces the summary screen, which prints the same words where the number would be |
| **A conflicts-only run closes over its own screen** | **New, one term.** A "notes left unchanged" warning tells you to see the summary screen, and that screen is not drawn for it, although it has a section built for exactly that list. Errors were added to the condition that opens the screen; conflicts were not |
| **The mapping-import window prints `[object Object]` in place of the error** | **Closed 2026-08-30.** Each error is named, the window stays open on a failed run, and the errors are listed on a screen. One exit remains on that window, for an unreadable source file, which still reports through the truncating notice the rest of it stopped using |
| Home and grouping notes are still matched by location | **Answered by the reframing, not yet shippable.** They reconcile through the identity index like every other note, and under the rule that a refresh never changes a folder the alias keeping the old identifier alive is always reconstructed against the folder it was written under. The conditional part is gone. What remains is the collision half below |
| **May a grouping note's identity be independent of its folder?** | **Half answered.** Under the new rule the survive-a-move half no longer needs an answer, because nothing moves without being asked. The collide half is still live: two imports of one framework into two folders claim the same grouping identifiers. Still an owner call |
| Two of the blocking findings are small and deterministic | **Both closed on the blocked branch, unreleased.** The enrichment phase is now told which overwrite setting is in force, and a suppressed move reports the folder the note is in rather than the one it would have gone to. Neither ships while the branch is blocked |
| Moves and orphans are recorded and never shown | **Closed on the finish message, and still wrong in one case.** Both counts now ride on the notice for every run, so a clean refresh states its zeros instead of closing silently. But the orphan count is read from a field the engine leaves unset both when there are none and when the check never ran, so a suppressed check still reports "No orphans." See the row below |
| Two renderings of one framework still share a curated folder | **Open, and it is the original defect in miniature.** The hierarchical and flat NIST CSF exports both resolve to `NIST CSF 2.0`, so the second is offered as a refresh of the first. Either the curated folders distinguish the rendering, or the ambiguity is put to the user |
| Switching source file keeps a typed destination | **Open, one-line fix.** Both source-reset sites clear the curated destination and neither clears the typed one, so picking a source, typing a destination, then switching sources sends the second into the folder belonging to the first |
| The seed change itself | **Applied, not yet committed, and one half of it is now moot.** `visual-workbench.spec.ts` completes a generation for the first time and needs no ownership answer, because the destination fix removed the ambiguity it could not express. `visual-workspace-flow.spec.ts` still matches the identifier rather than the rendered title and is still failing on that string |
| `tests/e2e/first-run.spec.ts` has an intermittent startup hang | On two consecutive runs of the same command on an idle host, one passed in 5.1s and one hung for 2m38s with an unresponsive renderer, failing on the first screenshot. The configuration fix is verified; the spec's stability is not, on one green run |
| `tests/e2e/first-run-vault/.obsidian/plugins/` is untracked build residue and is not gitignored | A clean run deletes it, a terminated one strands it. Nothing under that subdirectory is tracked, so ignoring it untracks nothing |
| `reference/settings.mdx` says the index file lives "relative to the vault root" | It does not. It lives in browser-managed storage outside the vault. The settings UI string says the same thing. A copy fix on both surfaces, not scheduled |
