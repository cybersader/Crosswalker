<Aside type="note" title="What this page is — a 101 on data morphology">
A progressive, intuitive **101 on data morphology**: the shared *language* for how data is shaped and reshaped. The aim is that when you meet a `transpose`, a `pivot`, a `sum`, or an x/y chart, you can name *exactly* what's happening — "oh, that's a reshape, not a transform" — instead of lumping it all into "the table." It's deliberately broad and a little verbose; that's the point. Crosswalker is the **application**: this is the mental model the whole tool is built and described in, but the model itself is plain data science that applies to a spreadsheet, a SQL table, or an ontology alike.
</Aside>

## The name: data morphology

**Data morphology** — the study of the *forms* data takes, and the operations that transform one form into another. ("Morphology" is the study of form.) Naming it buys two things: an **intuitive mental model** and a **shared vocabulary** — so you can say precisely *what shape is this, which operation am I applying, what shape am I rendering*, instead of blurring all three into "the table." None of this is invented here; it's plain data science (the established grammars it borrows from are spelled out below). What's useful is holding it as *one* coherent model — and that model is the language Crosswalker is built and described in.

## The mental model: shape, then three knobs

The goal is an **intuitive mental model**, not an academic chart. Hold this: data has a **shape**, and then there are **three independent knobs**. Almost every confusion (*"is a pivot a join?"*, *"transpose vs x/y axes"*) is from mixing the knobs.

> **Shape** what you've got → turn three knobs: **what it says** · **how it's laid out** · **how it looks**.

| | Plain question | The knob controls… | Everyday words |
|---|---|---|---|
| **Shape** | what *kind* of thing is this? | the native form | list · tree · web · timeline |
| **① Transform** | what should it **say**? | the *content* — which facts are present | keep (`filter`) · merge (`join`) · total (`sum`) |
| **② Reshape** | how is it **laid out**? | the *grid layout* — same facts, moved | `transpose` · wide ↔ tall · roll-up / drill-down |
| **③ Draw** | how should it **look**? | the *picture* — facts → visuals | x / y axes · color · bars vs dots |

**The one rule that resolves everything:** the three knobs are independent.
- **Transform** changes the *facts* — a sum removes rows, a join adds columns.
- **Reshape** changes the *layout*, never the facts — transpose is the same data, spun.
- **Draw** changes the *picture*, never the layout — x/y axes is a visual choice.

"Is a pivot a join?" No — a pivot turns all three knobs at once (total → spread wide → put on axes), which is why it feels like one big thing. Pull the knobs apart and it's obvious. Everything below is the rigorous backing for these four moves.

## The instinct that started this: a pivot is not a join

"A pivot could also be a left join — is that a thing?" No — and the *no* is the whole point. **Joining combines rows; summing collapses them. They are different families of operation.** A pivot is fundamentally a **group-and-aggregate** (OLAP), not a join. The join is an *optional upstream step* (to pull in unmapped rows so gaps show). Disentangling that is what this taxonomy is for. (See the [four dials log](/crosswalker/agent-context/zz-log/2026-06-03-four-dials-join-shape-layout-view/) — this extends it from 4 dials into a fuller stack.)

## Operation families — the meat (and the join-vs-sum split)

The existing [query-primitives](/crosswalker/concepts/query-primitives/) page lists 8 operations *flat*. The missing first-principles move is to **group them by what they fundamentally do to a row-set**, grounded in established theory:

| Family | What it does to rows | Primitives (ours) | Theory it comes from |
|---|---|---|---|
| **Reshape / select** | keep/drop rows + columns; derive new columns | `filter` · `project` · `bind` | relational algebra (σ select, π project) |
| **Combine / relate** | *widen* — stitch two row-sets on a key | `join` (inner/left/right/full/**anti**/semi) · `set-op` (∪ ∩ −) | relational algebra (⋈, ∪, −) |
| **Summarize / reduce** | *collapse* — many rows → one summary per group | `aggregate` (group-by + count/sum/avg/min/max/density) | **OLAP** — a GROUP BY *extension* to classic RA, not RA itself |
| **Traverse** | *follow edges* — walk the graph, transitively | `traverse` (hop · transitive closure · neighborhood) | Datalog / SPARQL property paths (`p*`) — beyond RA |
| **Compare** | delta between two snapshots | `diff` | version/ontology-specific |

**The key distinctions to internalize:**
- **Combine widens, summarize collapses.** A join adds columns (more about each row); an aggregate removes rows (fewer, summarized rows). Opposite directions.
- **A pivot = combine (assemble) → summarize (group by row-axis × col-axis, aggregate a measure) → present as a matrix.** So a pivot belongs to the *summarize* family wearing a *view shape*. "Pivot = left join" was a category error: the left join, if present, is the *combine* step feeding it.
- **Traverse is its own thing.** Following `broader`/`maps-to` edges transitively (CSF → 800-53 → CRI) is neither a join nor an aggregate — it's graph reachability (recursive). Classic RA can't even express it; that's why Tier 2 uses recursive CTEs.

| Shape | Structure | In Crosswalker |
|---|---|---|
| **Relation / table** | a set of tuples (rows × columns) | a *projection* of concepts/edges for one question |
| **Tree / hierarchy** | mono-parent nesting | a framework's internal structure (SKOS `broader`) |
| **Graph** | nodes + typed edges, many-to-many | **the substrate** — concepts are nodes, mappings + hierarchy are edges |
| **Sequence** | ordered list | versions, timelines, audit trail |

**Graph is the most general of the four** — a list is just a graph with no edges; a tree is a graph where every node has exactly one parent. So the deep move is: hold your data in the most general shape that fits (usually a graph), then treat every table, tree, or matrix as a **projection** of it for one question. That's the whole game — *one shape underneath, many projected views on top*. (Crosswalker takes this literally: an ontology **is** a graph of concepts + typed edges, and every view of it — a coverage matrix, a gap list — is a projection.)

## The trivialized taxonomy already exists — borrow it

The relief: this is **well-trodden ground in data science**, already compressed into small, learnable "grammars." We don't invent data morphology — we adopt these and point them at ontology/graph data. This is what should inform how the tool names everything it does at the query / output / projection piece.

| Layer | Established grammar | The trivialized verb set | Crosswalker mapping |
|---|---|---|---|
| **Shape** | **Tidy data** (Wickham 2014) | rows = observations, cols = variables; long vs wide | data shapes (relation / tree / graph / sequence) |
| **Transform** | **Grammar of data manipulation** (dplyr; relational algebra, Codd 1970) | one-table: `filter` · `select` · `mutate` · `arrange` · `summarise`+`group_by`; two-table: `join` (inner/left/right/full/anti/semi) · set-ops (∪ ∩ −) | reshape + combine + summarize families |
| **Reshape** | **OLAP cube ops** + pivot (`tidyr`) | `transpose` · long↔wide (`pivot_longer`/`pivot_wider`) · roll-up · drill-down · slice · dice | layout change *without* changing content |
| **Project / present** | **Grammar of graphics** (Wilkinson 1999; ggplot2, Wickham 2010) | data → aesthetics (`x`, `y`, `color`, `size`) → geometry (bar/point/tile/line) → facets / coords | view shapes (table / pivot / graph / hierarchy / timeline) |

**The clarifying payoff** — the Excel examples live in *different* layers:
- **`transpose`** (swap rows ↔ cols) is **reshape** — same content, different layout.
- **"x / y axes"** is **project** — mapping a column to a visual position (an *aesthetic*); the grammar-of-graphics move.
- Excel blurs them into "the pivot table"; data morphology keeps them apart. A pivot table is literally *group + aggregate* (transform) → *long-to-wide* (reshape) → *x = rows, y = cols, fill = measure* (project).

So **one concept page is enough**: **Shape · Transform · Reshape · Project**, each a one-paragraph borrow from an existing grammar, then "here's how Crosswalker exposes it." The operation-families list above folds into **Transform**; reshape + project are the two layers it was missing.

## Candidate views for the GRC corpus (the practical payoff)

Each view = a transform + a reshape + a projection. This menu is what to pull from as we test the audit/compliance library:

| View | Question it answers | Operation family | View shape | Status |
|---|---|---|---|---|
| **Coverage matrix** | where do framework A & B overlap? | summarize (count) | pivot | ✅ built |
| **Coverage density** | how heavily is each area mapped? | summarize (count, grouped) | table / pivot | ✅ built |
| **Gap / orphan** | which controls have *no* coverage? | combine (**anti-join**) | list / table | next |
| **Overlap** | controls in *both* A and B | combine (set-op ∩) | list | buildable |
| **Only-in-A** | in A but not B | combine (set-op −) | list | buildable |
| **Crosswalk chain** | A → B → C transitive reach | traverse (closure) | graph / list | closure shipped |
| **Bidirectional lookup** | what maps to X (either direction)? | reshape (filter) | table | ✅ built |
| **Confidence-weighted coverage** | strong vs weak coverage | summarize (avg/sum of confidence) | pivot heatmap | buildable |
| **Version diff** | what changed v1 → v2? | compare (diff) | table | primitive shipped |
| **Framework-pair density** | which framework *pairs* are densest? | summarize (group by pair) | table | buildable |

The pattern: most "compliance questions" are one operation family + one shape. Naming the family first tells you which primitive to reach for and which shape fits.
