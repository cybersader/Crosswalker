## §1 Why this page exists

The [Foundation phase](/crosswalker/reference/roadmap/) intro states: *"The three interconnected schemas (_crosswalker metadata, ImportRecipe, [StewardshipProfile](/crosswalker/agent-context/zz-log/2026-05-01-foundation-commitments-and-followon-research/)) must be designed together — getting any wrong is expensive to fix later."* The [v0.1 stack-pivot](/crosswalker/agent-context/zz-log/2026-05-02-v0-1-initial-stack-pivot/) makes this concrete by committing to a buildable Tier 1 + Tier 2 sidecar architecture.

This page is the **unified v0.1 schema reference**. It distinguishes governing [Schema Contracts](/crosswalker/concepts/terminology/#schema-contract), the artifacts they govern, and derived representations:

1. **Tier 1 Schema Contract** — [`spec/tier1.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/tier1.schema.json) governs canonical Tier 1 member-record representations, including `_crosswalker` provenance, concept records, crosswalk assertions, and junction/evidence assertions.
2. **Recipe Schema Contract** — [`spec/recipe.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/recipe.schema.json) governs **ImportRecipe**, an intensional Recipe subtype that drives generation but remains outside Tier 1 knowledge.
3. **Tier 1 record shapes** — `_crosswalker` metadata and the junction-note/crosswalk/concept discriminators are member representations within concrete [Knowledge Sets](/crosswalker/concepts/terminology/#knowledge-set). v0.1 does **not** claim a generalized `KnowledgeSet` aggregate schema.
4. **Tier 2 sidecar SQL representation** — a qualified Tier 1 → Tier 2 projection into queryable SQLite. Tier 2 is deletable and recoverable from Tier 1.

[Artifact roles and authority](/crosswalker/concepts/artifact-roles-and-authority/) is the governing conceptual model: Schema Contracts govern; Knowledge Sets are extensional; Recipes are intensional; future Execution Records and Package Manifests are separate administrative envelopes.

The earlier-written [config-schema-design](/crosswalker/agent-context/config-schema-design/) and [constraint-enforcement](/crosswalker/agent-context/constraint-enforcement/) pages stay as background design rationale; this page is the consolidated v0.1 build target.

### Naming history: FrameworkConfig → ImportRecipe

The type now called **`ImportRecipe`** was originally proposed as `FrameworkConfig` in the [config-schema-design](/crosswalker/agent-context/config-schema-design/) page (2026-04). On 2026-05-03 the name was changed for two reasons:

1. **General-ontology positioning.** "Framework" baked the GRC use case into a type that's actually general — any structured ontology (compliance frameworks, biomedical taxonomies, library classifications, custom domain hierarchies) can be imported via this recipe. "Ontology" is the broader term that already pervades the project's vocabulary ([ontology lifecycle](/crosswalker/concepts/ontology-lifecycle/), [ontology evolution](/crosswalker/concepts/ontology-evolution/), ontology diff primitives).
2. **Recipe vs config.** "Config" sounds like *settings*; this artifact is actually a *reusable transformation recipe* applied to a source. A recipe is shareable, version-controlled, and replayable — semantics that "config" doesn't carry.

Companion field renames in `_crosswalker` metadata and junction-note schemas:

- `framework_id` → `ontology_id`
- `framework_version` → `ontology_version`
- `framework` (junction-note field) → `ontology`
- `config_id` (in `_crosswalker`) → `recipe_id`

Folder convention (`Frameworks/...`) is **user-controlled** via `recipe.output.base_path` — examples in this doc still use `Frameworks/NIST-800-53-r5/` because NIST 800-53 *is* a framework and that's the natural choice; non-GRC users would set `base_path` to `Ontologies/`, `Standards/`, `Domain/X/`, etc.

Historical decision logs (`zz-log/`) and research deliverables (`zz-research/`) are **preserved verbatim** with the original `FrameworkConfig` / `framework_id` naming — they are dated decision records, not living spec.

## §2 The schemas at a glance

```
   GOVERNING CONTRACTS AND ADJACENT INTENT

   ┌─ Recipe Schema Contract ─────┐       ┌─ Tier 1 Schema Contract ────┐
   │ governs ImportRecipe         │       │ governs Tier 1 records      │
   └──────────────┬───────────────┘       └──────────────┬──────────────┘
                  │                                       │ validation
                  │ governs generation                    │
                  ▼                                       ▼
   structured source + ImportRecipe ──► render/generate/validate
                                                  │
                                                  ▼
   TIER 1 — CANONICAL CROSSWALKER-MANAGED REPRESENTATION/AUTHORITY
   ┌──────────────────────────────────────────────────────────────────┐
   │ Markdown member records representing one or more Knowledge Sets │
   │                                                                  │
   │ ┌────────────────┐ ┌──────────────────┐ ┌─────────────────────┐ │
   │ │ concept record │ │ junction/evidence│ │ crosswalk assertion │ │
   │ │ + _crosswalker │ │ assertion record │ │ record              │ │
   │ └────────────────┘ └──────────────────┘ └─────────────────────┘ │
   │                                                                  │
   │ No generalized KnowledgeSet aggregate schema is claimed.        │
   │ ImportRecipe remains outside this Tier 1 knowledge boundary.     │
   └───────────────────────────────┬──────────────────────────────────┘
                                   │ qualified Tier 1 → Tier 2 projection
                                   ▼
   TIER 2 — SQLITE SIDECAR (DERIVED, DELETABLE, REPRODUCIBLE)
   ┌──────────────────────────────────────────────────────────────────┐
   │ tables: mappings · junction_notes · concepts · ontologies        │
   │ indexes and closure cache for query acceleration                 │
   └──────────────────────────────────────────────────────────────────┘
```

**Cross-contract and representation invariants** (load-bearing):

- The Recipe Schema Contract governs ImportRecipe; the Tier 1 Schema Contract governs generated member records. Validity in one contract does not imply validity in the other.
- ImportRecipe remains adjacent intensional policy, not Tier 1 ontology/mapping content.
- Every field in the Tier 2 SQL representation must be derivable from Tier 1 frontmatter.
- Every Tier 1 frontmatter field that needs to be queryable in Tier 2 must be a flat scalar or a wikilink (no nested objects, no inline expressions). [Bases-queryable](/crosswalker/concepts/metadata-ecosystem/) constraint.
- Managed ownership is declared: Crosswalker updates only recipe-managed top-level fields plus `_crosswalker`; `user_preserve` fields remain untouched.
- Junction notes are generated member records, but users can edit them; v0.1 generation is non-destructive.
- ImportRecipe may be bundled, imported, instantiated from a template, or edited through the workbench. Its canonical specification is preserved separately from implementation-only `ImportMapping`, `RecipeDocument`, `SavedConfig`, and draft state.

## §3 Tier 1 frontmatter contract (canonical Markdown records)

Tier 1 (the canonical Markdown representation) is governed by [`spec/tier1.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/tier1.schema.json). A recipe may manage declared top-level fields, while `user_preserve` fields remain user-owned. Every generated record also carries `_crosswalker` provenance (where the record came from).

### `_crosswalker` provenance block

| Field | Required | Meaning |
|---|---:|---|
| `spec_version` | Yes | Tier 1 contract version used to write the record |
| `source_ref` | Yes | Stable or human-readable source reference |
| `produced_at` | Yes | ISO 8601 production timestamp |
| `producer` | No | Producer name and version |
| `recipe` | No | Recipe identifier and content hash used for this output |
| `import_set` | No | Durable ownership stamp: `id` matches `^iset-[a-z0-9]{6}$`; `scheme` is fixed at mint. The closed enum is `endpoint-v1 | set-qualified-v1` (source: `spec/tier1.schema.json § $defs.provenance_block.properties.import_set.properties.scheme.enum`) |
| `concept_cid` | No | Content identifier for the declared concept-identity scope; layout and mapping-only defaults do not enter a concept's scope |


Crosswalk assertion identity (the stable name of one mapping note) follows the owning set's fixed scheme. Both values and forms below are defined by `spec/tier1.schema.json § $defs.provenance_block.properties.import_set.properties.scheme`:

- `endpoint-v1`: `cw-<sanitized-subject>-<sanitized-object>`. This is the original form and remains byte-identical on refresh.
- `set-qualified-v1`: `cwset-<import-set-id>-<sanitized-subject>-<sanitized-object>`. The `cwset-` marker makes the form visibly distinct; the minted set id lets equal endpoint pairs in different import sets coexist. Row order and mapping-set metadata do not enter either form.

A refresh always reuses the stored scheme. Choosing coexistence mints a new import set whose assertions use `set-qualified-v1`; no existing note is migrated, moved, or re-identified. See the [import-set ownership decision](/crosswalker/agent-context/zz-log/2026-08-21-import-set-ownership/#how-this-dissolves-release-isolation-rather-than-mitigating-it).

### Concept-note fields

A CURIE (a compact stable identifier such as `nist:AC-2`) identifies the concept independently of its vault path.

| Field | Required | Meaning |
|---|---:|---|
| `curie` | Yes | Stable concept identity |
| `_crosswalker` | Yes | Provenance block above |
| `title` | No | Display title |
| `aliases` | No | Alternate names |
| `tags` | No | Obsidian tag paths |
| `parent` | No | Clickable parent wikilink, or wikilink array for display polyhierarchy |
| `parent_curie` | No | Stable identity of the one canonical parent projected to Tier 2; it is never inferred from `parent` |
| `children` | No | Optional child wikilinks |

### Junction-note fields

A junction note (one evidence relationship represented as its own note) keeps endpoint identity separate from endpoint address.

| Field | Required | Meaning |
|---|---:|---|
| `curie` | Yes | Stable junction-note identity |
| `subject` | Yes | Clickable subject wikilink |
| `predicate` | Yes | Relationship type |
| `object` | Yes | Clickable object wikilink |
| `_crosswalker` | Yes | Provenance block above |
| `kind` | No | When present, fixed to `junction-note` |
| `subject_curie` | No | Stable subject identity; never inferred from `subject` |
| `object_curie` | No | Stable object identity; never inferred from `object` |
| `coverage` | No | `full`, `partial`, `none`, or `n/a` |
| `reviewer`, `review_date`, `status`, `confidence` | No | Review and lifecycle facts |
| `scope`, `expires_at`, `notes`, `tags` | No | Scope, expiry, annotation, and Obsidian tags |

### Crosswalk-edge fields

A mapping set (one published collection of mapping assertions) gives repeated assertions and separate releases independent provenance. An assertion occurrence (one row from one mapping-set release) receives its own deterministic `curie`; the schema does not require every producer to use one particular CURIE algorithm.

| Field | Required | Meaning |
|---|---:|---|
| `curie` | Yes | Stable identity of this assertion occurrence |
| `subject_id` | Yes | Subject concept CURIE |
| `predicate_id` | Yes | One of the 6 relationship predicates defined by `spec/tier1.schema.json § $defs.crosswalk_edge_frontmatter.properties.predicate_id` |
| `object_id` | Yes | Object concept CURIE |
| `_crosswalker` | Yes | Provenance block above |
| `kind` | No | When present, fixed to `crosswalk-edge` |
| `mapping_set_id` | No | Non-blank stable identifier for the mapping-set release; writers trim surrounding whitespace, then preserve case and content |
| `predicate_modifier` | No | Predicate modifier (a flag changing assertion meaning). The only valid value is `NOT`; absence means a positive assertion |
| `match_type`, `match_confidence` | No | SSSOM-shaped match classification and confidence |
| `mapping_justification`, `mapping_provider`, `mapping_date` | No | Why, from where, and when the mapping was asserted |
| `creator_id`, `review_status`, `tags` | No | Creator, review state, and Obsidian tags |

### Additive compatibility

All six 2026-08-21 additions are optional at their containing-record boundary: `parent_curie`, `subject_curie`, `object_curie`, `mapping_set_id`, `predicate_modifier`, and `_crosswalker.import_set`. When `import_set` is present, both its `id` and `scheme` are required (source: `spec/tier1.schema.json § $defs.provenance_block.properties.import_set`). Legacy Tier 1 records without an ownership stamp therefore continue to validate. Producers clear a declared managed field when its rendered source becomes empty, but never clear a `user_preserve` field.

## §4 Recipe Schema Contract and ImportRecipe specification

ImportRecipe is a concrete [Recipe](/crosswalker/concepts/terminology/#recipe) subtype: a portable, machine-evaluable declaration of intended source-to-Tier-1 behavior. It is governed by the Recipe Schema Contract and sits adjacent to generation; it is not embedded inside the Tier 1 Knowledge Set it helps produce.

| Recipe role | Meaning in v0.1 |
|---|---|
| **Specification** | The canonical ImportRecipe JSON governed by `spec/recipe.schema.json`. |
| **Template** | Parameterized/default policy, such as a Shape Preset, used to instantiate or initialize a specification/mapping. |
| **Binding** | A Recipe reference plus concrete source identity and selected parameters. |
| **Execution** | One application of a bound Recipe. Verified run facts belong in a later separate Execution Record, not in mutable Recipe intent. |

:::tip[Current machine-readable contract — verified 2026-08-21]
The authoritative v0.1 contract is [`spec/recipe.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/recipe.schema.json), summarized in the [portable-recipe fidelity synthesis](/crosswalker/agent-context/zz-log/2026-07-21-portable-import-recipe-fidelity-synthesis/). It uses the settled closed grammar (`folder | file | heading | tag | wikilink`) plus `also_emit`, enrichment, graph edges, and optional query declarations.

The active import workbench now retains the full validated canonical recipe through a lossless `RecipeDocument` boundary. This is **internal/in-memory fidelity**, not yet a durable user recipe library: save/open/export/share UI under `_crosswalker/recipes/import/` remains deferred.
:::

Current additive fields include:

- optional display metadata and structured `metadata.based_on` ancestry;
- optional `source.version` as compatibility metadata, never stronger than verified run provenance;
- ordered `target.also_emit.body` projections (`append | section` × `text | code | quote | list`);
- typed managed scalar coercion through the closed `number` template filter;
- omission-safe identity templates through first-position `optional` and empty-safe `curie-prefix(prefix)` controls;
- deterministic normalized equality and canonical JSON serialization;
- four validation layers: JSON Schema, recipe semantics, source compatibility, and editable-model portability.

:::caution[Historical design sketch below]
The TypeScript shape and YAML example below predate the May 2026 primitive-grounded recipe decision and are retained as naming/design history. They are **not** the current serialized schema. Read the [Ch 20 synthesis](/crosswalker/agent-context/zz-log/2026-05-03-import-primitive-formal-foundation-synthesis/), [Ch 22 target-structure synthesis](/crosswalker/agent-context/zz-log/2026-05-04-target-structure-synthesis/), and machine-readable schema before implementing against this section.
:::

An ImportRecipe is a portable, deterministic instruction artifact. Bundled recipes currently drive recognition and generation; persistent user-authored recipe-file lifecycle is the next UI/storage slice.

### TypeScript shape

```typescript
interface ImportRecipe {
  // === Identity ===
  schema_version: 'import-recipe-v1';
  id: string;                          // 'nist-800-53-r5' (machine-readable, stable)
  name: string;                        // 'NIST SP 800-53 Rev 5'
  version: string;                     // 'Rev 5 Update 1'
  description?: string;
  tags?: string[];                     // ['compliance', 'nist', 'security-controls']
  author?: string;                     // for shared configs
  upstream_url?: string;               // canonical source URL

  // === Source matching (for fingerprint-based auto-detection) ===
  source_file_patterns?: string[];     // glob patterns: ['sp800-53*.xlsx', 'NIST_800-53_*.csv']
  fingerprint_columns?: string[];      // columns whose presence identifies this ontology
  expected_min_rows?: number;          // sanity check
  expected_max_rows?: number;

  // === Sheet selection (XLSX only) ===
  sheets?: SheetConfig[];

  // === Column mapping & roles ===
  columns: ColumnConfig[];

  // === Transforms ===
  transforms?: TransformConfig[];

  // === Output preferences ===
  output: OutputConfig;

  // === StewardshipProfile reference (for evolution tracking, optional in v0.1) ===
  stewardship_profile_id?: string;     // links to StewardshipProfile registry entry

  // === Crosswalk definitions (link this ontology to others) ===
  crosswalks?: CrosswalkConfig[];

  // === Sharing metadata ===
  exported_at?: string;                // ISO 8601
  exported_from?: string;              // 'crosswalker-0.2.0'
  compatibility?: string;              // minimum plugin version (semver)
}

interface SheetConfig {
  name: string;                        // 'SP 800-53 Revision 5'
  header_row?: number;                 // 0-indexed, default 0
  purpose: 'primary' | 'mapping' | 'supplementary';
  merge_key?: string;                  // column to join on when merging sheets
}

interface ColumnConfig {
  source_name: string;                 // exact column header in source file
  role: ColumnRole;
  output_field?: string;               // where it lands in frontmatter (default = role-derived)
  transforms?: TransformConfig[];      // column-specific transforms
  required?: boolean;                  // import fails if column missing
}

type ColumnRole =
  | 'control_id'                       // primary key for control notes
  | 'control_name'                     // title
  | 'control_text'                     // body content
  | 'hierarchy'                        // determines folder nesting (multiple allowed)
  | 'frontmatter'                      // arbitrary frontmatter field
  | 'tag'                              // emit as tag
  | 'crosswalk_target'                 // value identifies a crosswalk target node
  | 'evidence_link'                    // value is a wikilink to an evidence document
  | 'metadata'                         // SSSOM/STRM metadata field (confidence, mapping_date, etc.)
  | 'ignore';

interface TransformConfig {
  type: 'tag-aggregation' | 'id-normalization' | 'hierarchical-ffill'
      | 'preamble-extraction' | 'split' | 'join' | 'regex-replace'
      | 'lowercase' | 'uppercase' | 'trim' | 'array-from-delimited'
      | 'date-parse' | 'number-parse' | 'lookup' | 'custom';
  params: Record<string, unknown>;
  // 24 transform types per the Foundation transform engine commitment;
  // 'custom' allows JSONata or Arquero escape hatches
}

interface OutputConfig {
  base_path: string;                   // 'Frameworks/NIST-800-53-r5'
  folder_structure: 'flat' | 'hierarchical';
  filename_template: string;           // '{control_id}.md'
  note_template?: string;              // Handlebars template for body; default = built-in
  empty_handling: 'skip' | 'create_with_placeholder' | 'merge';
  array_handling: 'wikilinks' | 'tags' | 'inline_list';
  key_naming_style: 'snake_case' | 'kebab-case' | 'camelCase';
}

interface CrosswalkConfig {
  // Per-config crosswalk definitions; produces crosswalk edges as STRM-predicate frontmatter
  source_ontology: string;            // self-reference: this config's id
  target_ontology: string;            // target ontology id
  source_column: string;               // column in source data that identifies the link
  target_match_column?: string;        // column in target ontology to match against
  match_mode: 'exact' | 'array_contains' | 'regex' | 'fuzzy';
  predicate: 'is_equivalent_to' | 'is_broader_than' | 'is_narrower_than'
           | 'is_approximate_to' | 'intersects_with' | 'no_relationship';
  link_direction: 'source_to_target' | 'target_to_source' | 'bidirectional';
  default_metadata?: SssomMetadata;    // applied to all generated edges
}

interface SssomMetadata {
  // SSSOM envelope fields (see §6 for the full hybrid resolution)
  mapping_justification?: string;      // SEMAPV vocabulary
  confidence?: number;                 // 0.0 - 1.0
  author_id?: string[];                // ORCIDs for SSSOM authors
  mapping_date?: string;               // ISO 8601
  mapping_tool?: string;               // 'crosswalker-0.2.0'
  predicate_modifier?: 'NOT';
  comment?: string;
}
```

columns:

### SavedConfig, ImportMapping, and ImportRecipe boundary

The earlier v1→v2 migration sketch is superseded by the canonical-fidelity boundary implemented in 2026-07-21.

| Object | Current role | Authority |
|---|---|---|
| **SavedConfig** | Legacy fingerprint-bound wizard convenience state | Not a canonical portable Recipe and not auto-migrated into one |
| **ImportMapping** | Editable source-bound workbench projection over Recipe-owned fields | Implementation/editor state; never the preservation authority |
| **RecipeDocument** | In-memory preservation/editor transaction boundary around original + editable projection | Preserves the original canonical ImportRecipe while edits patch owned regions |
| **ImportRecipe** | Portable Recipe specification governed by the Recipe Schema Contract | Canonical instruction artifact |

The workbench must patch a validated original rather than rebuild a Recipe from SavedConfig or ImportMapping. See the [portable-recipe fidelity synthesis](/crosswalker/agent-context/zz-log/2026-07-21-portable-import-recipe-fidelity-synthesis/).

### §4.5 Recipe `query:` block (added v0.1.6 — SchemaVer 1.1.0; additive)

Per [Ch 31 schema design](/crosswalker/agent-context/zz-research/2026-05-08-challenge-31-deliverable-a-shape-dispatched-data-only/) + [Ch 36 compositional language stack](/crosswalker/agent-context/zz-research/2026-05-09-challenge-36-query-language-rerun/), v0.1.6 added an optional `query:` block to the recipe schema. Recipes can now declare WHAT to query (axes, edges, aggregation) without writing SQL — the engine compiles the declared block to SQL recursive CTEs against the Tier 2 sqlite-wasm cache.

**Backward compatibility**: existing recipes WITHOUT `query:` continue to validate. The bump is purely additive (SchemaVer ADDITION); SchemaVer URI did NOT bump (`https://crosswalker.dev/spec/recipe.schema.json` stays).

### §4.6 Layout-entry `variadic` block (added 2026-07-05 — SchemaVer 1.2.0; additive)

A fixed layout lists its folder levels ahead of time — one `layout_entry` per level. Ragged ids carry a **different number of pieces per row** (ATT&CK `T1055` vs `T1055.011`; any parent/child id family), so no fixed list fits every row — the result was a flat dump. A folder `layout_entry` can now carry an optional **`variadic`** block that explodes the entry's rendered scalar *after* templating (templates stay scalar — one value in, one value out) into a **variable number of folder levels**.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes WITHOUT `variadic` validate and render byte-identically. The spec URI did NOT bump (`https://crosswalker.dev/spec/recipe.schema.json` stays). `variadic` is schema-constrained (layout_entry `allOf` if/then) to `mechanism: "folder"` only — heading/tag variants are deferred.

**Fields:**

| Field | Type | Default | Meaning |
|---|---|---|---|
| `delimiter` | string (required) | — | What the rendered scalar is split on (e.g. `.` for ATT&CK ids). |
| `segment` | `prefix` \| `part` | `prefix` | Folder-name shape. `prefix`: cumulative prefixes joined by the delimiter (`X.Y.Z` → `X`, `X.Y`) — globally-unique, CSF-convention. `part`: raw pieces (`X.Y.Z` → `X`, `Y`). |
| `drop_last` | boolean | `true` | Drop the leaf piece before building folders — the `file` entry names it with the full id anyway. |
| `max_depth` | integer ≥ 1 | `6` | Safety cap on folder levels produced. |
| `on_overflow` | `truncate` \| `error` | `truncate` | Past `max_depth`: `truncate` keeps the first `max_depth` + records a `variadic-overflow-truncated` deviation note (no data loss — full id is in the filename); `error` fails the render. |

**Semantics** (exact): render `template` → scalar → split on `delimiter` (empty pieces dropped, each → a `folder-level-skipped` note) → if `drop_last`, drop the final piece → build segments per `segment` mode → cap at `max_depth` → append each as a folder level (same path as fixed folders). Zero segments (a top-level id) is normal, not a deviation. Deterministic: segments derive only from the row's own value.

**Example** (ATT&CK technique nesting — `T1055` and `T1055.011` from one recipe):

```yaml
layout:
  - level: root
    mechanism: folder
    template: Techniques
  - level: technique
    mechanism: folder
    template: "{external_id}"
    variadic:
      delimiter: "."
      segment: prefix     # T1055.011 → parent folder T1055
      drop_last: true     # leaf piece belongs to the file
      max_depth: 6
      on_overflow: truncate
  - level: technique
    mechanism: file
    template: "{external_id}.md"
```

`T1055` → `Techniques/T1055.md` (no parent folder); `T1055.011` → `Techniques/T1055/T1055.011.md`.

**Scope**: recipe-only in this round — the import wizard doesn't yet propose or edit `variadic` (planned follow-up: detect the ragged-id signature — a delimiter appearing in ~20–79% of rows — and offer variable-depth nesting). The full folder-note convention (`T1055` *becoming* the `T1055/` container as `T1055/T1055.md`) is a separate batch-scoped post-pass still under design.

### §4.7 `also_emit.frontmatter.managed_links` (added 2026-07-10 — SchemaVer 1.3.0; additive)

Single-value links live in `managed` as a scalar `"[[…]]"` string (`parent: "[[T1078]]"`). A **multi-value** link column — a cell holding several ids (`Related Controls: "AC-2, AC-3, PM-9"`) — needs a YAML **array** of wikilinks so each id is an indexable graph edge, not one dead `[[AC-2, AC-3, PM-9]]` string. `managed_links` is that region.

Each key maps to `{ template, split? }`. render() renders `template` to a scalar, splits it on `split` (default comma + semicolon), wraps each non-empty trimmed piece in `[[…]]`, and emits the key as an array. An empty cell omits the key entirely (an empty managed array would still clobber a user value on re-import). Regenerated wholesale on re-import (managed, not unioned).

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes WITHOUT `managed_links` validate unchanged. Spec URI unchanged.

```yaml
also_emit:
  frontmatter:
    managed_links:
      related:
        template: "{Related Controls}"   # bare cell value — render() wikilinks each piece
        split: [",", ";"]                 # optional; this is the default
```

`Related Controls: "AC-2, AC-3, PM-9"` → `related: ["[[AC-2]]", "[[AC-3]]", "[[PM-9]]"]`.

### §4.8 `target.enrichment` block (Pass 1.5; added 2026-07-10 — SchemaVer 1.3.0; additive)

`render()` is per-row pure (Pass 1, hashable). Four artifacts need **cross-row** knowledge, so an optional **batch-scope enrichment pass** runs *after* every row renders (`src/generation/enrich.ts`): children lists on parents, materialized facet hub notes, honest edge stats, and (reserved) folder-note placement. It never touches `render()`; determinism holds at batch level — every derived list is sorted by curie, hubs by path, so input order never leaks.

**Backward compatibility**: purely additive. Recipes WITHOUT `enrichment` emit nothing new and validate unchanged. Spec URI unchanged.

**Fields:**

| Field | Type | Default | Meaning |
|---|---|---|---|
| `children_lists` | boolean | `false` | Each parent note gains a managed `children` array of wikilinks to its direct children (derived from the same parent relation the parent link uses), sorted by child curie. Fully managed — regenerated wholesale on re-import (user extras inside the array are not preserved; `user_preserve` covers *separate* keys). |
| `facet_notes` | `none` \| `tags-only` \| `notes` | `none` | `none`: nothing beyond per-note facet tags. `tags-only`: facet tags only, no hub notes. `notes`: one synthetic hub note per facet **value** with a managed `members` list (sorted by curie), `kind: facet`, the facet tag, and an H1 body; user prose below the H1 survives re-import. Hubs materialize only for values with ≥2 members. |
| `parent_note` | `sibling` \| `folder-note` | `sibling` | Where a concept that is also a parent lives. `sibling`: `X.md` beside `X/`. `folder-note`: `X/X.md` — the batch enrichment pass relocates evidence-based (only parents whose children actually nest under their folder), resolves re-import write targets by curie so no duplicates arise, and relocates back symmetrically when set to `sibling` again. Streamed sources fall back to sibling with a deviation note (eager batch required). |
| `hub_note_folder` | string | *(output root)* | Optional vault-relative folder for materialized facet hub notes. |
| `level_hubs` | `none` \| `notes` | `none` | Added SchemaVer 1.4.0 (§4.9). Hierarchy hub/MOC index notes — one per folder level. |
| `waypoint_marker` | boolean | `false` | Added SchemaVer 1.4.0 (§4.9). Opt-in `%% Waypoint %%` marker on generated folder-note/hub notes. |

**Stats**: `GenerationResult.edgeCount` = parent links + children entries + facet-hub member entries + level-hub child-link entries — the review screen's "K graph edges" line (a run shipping 0 edges is a visible warning, not a silent dead graph).

**Preset defaults** (stamped by `instantiate` onto `ImportMapping.enrichment`, then serialized to `target.enrichment`): `browsable-framework` → `children_lists: true`, `facet_notes: "notes"`, `level_hubs: "notes"`. The hyperconnected default IS the default.

```yaml
target:
  enrichment:
    children_lists: true
    facet_notes: notes
    parent_note: sibling
    level_hubs: notes
```

**Scope**: recipe + preset land here; the workbench Connections-card UI knobs and the review-screen edge count are wired (§4.9 for the level-hubs/Waypoint-marker round). Folder-note relocation (step 2 of the design) is implemented in `src/generation/enrich.ts`.

### §4.9 `target.enrichment.level_hubs` + `waypoint_marker` (added 2026-07-11 — SchemaVer 1.4.0; additive)

Closes the [ICSB emitter-controls gap audit](/crosswalker/agent-context/zz-log/2026-07-11-shape-workbench-architecture-synthesis/#3-the-connectedness-mandate--vaults-must-be-graphs-not-filing-cabinets)'s #1-priority gap: Crosswalker had facet hub notes (value-grouping) but no hierarchy-*level* index/MOC concept, unlike the ICSB pipeline's `hubs.*` (Home + per-level MOCs, derived from the canonical model). Delivery detail (folder-note-as-default, per-import root folders, the review screen's exact-count plan) is in [`CHANGELOG.md` "Frameworks arrive furnished"](https://github.com/cybersader/crosswalker/blob/main/CHANGELOG.md#frameworks-arrive-furnished-2026-07-11-third-batch), not restated here.

**`level_hubs: 'notes'`** — every FOLDER level in the generated structure gets an index note, derived from the batch's own rendered note paths (never a filesystem scan):

- **Hosted**: when a folder's own concept note already exists in the batch (sibling `X.md` beside `X/`, or folder-note `X/X.md` — basename is the only identity that matters, since links in this codebase are basename-only), that note gains a managed body **"Contents"** section listing the folder's direct children (subfolders' hub identities + sibling notes, sorted by curie, as `[[wikilinks]]`).
- **Synthetic**: a folder with no such note (a pure structural grouping folder, or the per-import root) gets a brand-new hub note (`kind: 'hub'`, curie `<ontology>:hub/<folder-path-slug>`) at `<folder>/<folder>.md`.
- **Root hub**: the per-import root folder (`GenerationOptions.basePath`) gets a hub too, named after the folder — the import's "home" note.
- Re-import safe: the managed section is delimited by HTML-comment markers and stripped-and-reappended on regeneration (same discipline as `facet_notes`'s H1 split) — user prose elsewhere in the note survives.
- Default `'notes'` on the `browsable-framework` preset (the connectedness mandate — [shape-workbench synthesis §3](/crosswalker/agent-context/zz-log/2026-07-11-shape-workbench-architecture-synthesis/#3-the-connectedness-mandate--vaults-must-be-graphs-not-filing-cabinets)).

**`waypoint_marker: true`** — additionally appends the `%% Waypoint %%` trigger comment to every folder-note/hub note this import generates, so the [Waypoint community plugin](https://github.com/IdreesInc/Waypoint) can *also* track notes a user later adds to that folder by hand. Idempotent (never duplicates or strips a `%% Begin Waypoint %%` block Waypoint has already expanded). Additive, not a replacement — Crosswalker's own generated section stays the primary, always-on mechanism (Waypoint's directory-scan approach can't reconstruct the curated, edge-derived grouping Crosswalker's own model produces). Default `false`; the workbench only offers the toggle when a Waypoint-style plugin is detected enabled.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes without these keys validate and render unchanged. Spec URI did NOT bump.

### Filename convention

`Junctions/{ontology}/{control_id}--{evidence_slug}.md` — e.g., `Junctions/nist-800-53-r5/AC-2--MFA-Policy.md`.

The composite filename (control + evidence) makes diff-on-rename easy and prevents collision when one piece of evidence implements multiple controls.

### Mandatory vs optional fields (rule)

- **Mandatory (5)**: `link_type`, `evidence`, `control`, `ontology`, `status`. Plugin generation refuses to create a junction note missing any of these. Bases queries assume their presence.
- **Optional (8)**: `confidence`, `evidence_type`, `method`, `reviewer`, `review_date`, `responsible`, `collected`, `expires`. Pluginrenders missing as `null`/empty.
- **Computed**: `freshness` derived from `review_date` + `expires` at query time (Tier 1: in-memory; Tier 2: SQL view).

The OSCAL export pipeline is straightforward field-rename. See [`reference/registry/oscal`](/crosswalker/reference/registry/oscal/) for the mapping table once the OSCAL mental-model doc lands.

## §6 Crosswalk assertion vocabulary and SSSOM provenance

A crosswalk assertion (one stated relationship between two concepts) stores its relationship in `predicate_id` and any explicit negation separately in `predicate_modifier`. The 6 allowed predicates are sourced from `spec/tier1.schema.json § $defs.crosswalk_edge_frontmatter.properties.predicate_id`:

| `predicate_id` | Plain meaning |
|---|---|
| `is_equivalent_to` | The concepts have the same meaning for the mapping purpose |
| `is_broader_than` | The subject covers more than the object |
| `is_narrower_than` | The subject covers less than the object |
| `is_approximate_to` | The concepts are similar but not equivalent |
| `intersects_with` | The concepts overlap |
| `no_relationship` | The source explicitly asserts no relationship |

`predicate_modifier` is absent for a positive assertion or exactly `NOT` for explicit negation. Negation is not encoded by inventing an `_NOT` predicate name. A negative equivalence therefore remains `predicate_id: is_equivalent_to` plus `predicate_modifier: NOT`.

SSSOM (the Simple Standard for Sharing Ontological Mappings) provenance is carried by `mapping_set_id`, `match_type`, `match_confidence`, `mapping_justification`, `mapping_provider`, `mapping_date`, `creator_id`, and `review_status`. Direct SSSOM-style queries and export preserve mapping-set provenance and negation. STRM export omits negated assertions because STRM cannot represent that modifier without changing meaning.

## §7 Tier 2 sidecar SQL schema (sqlite-wasm projection)

The Tier 2 sidecar is a **deletable, recoverable projection** of Tier 1 frontmatter into SQLite tables. It exists to enable performant queries (transitive closure, multi-ontology joins, coverage matrices, perspective views) that are awkward over markdown frontmatter.

**Recovery property** (load-bearing): if `.crosswalker.sqlite` is missing, corrupted, or stale, the projector rebuilds it from canonical Tier 1 on next vault load. This is what makes Tier 2 risk-free to bundle in v0.1.

:::tip[Substrate choice — verified 2026-08-21]
v0.1 ships `@sqlite.org/sqlite-wasm` as the embedded query substrate. `sqlite-vec` remains a decoupled optional vector layer and is deferred; the next calendar-anchored packaging revisit is 2026-11-06. See the [Tier 2 substrate synthesis](/crosswalker/agent-context/zz-log/2026-05-04-tier-2-substrate-synthesis/) and [WASM-A pivot synthesis](/crosswalker/agent-context/zz-log/2026-05-06-wasm-a-pivot-synthesis/).
:::

### Current schema summary

`src/tier2/schema.sql` is the canonical DDL. Tier 2 currently ships as `tier2-sqlite-v4`. The table below cites every stored column by table so additions are reviewable without copying a second SQL source that can drift.

| `junction_notes` | `vault_path`, `curie`, `subject`, `subject_curie`, `predicate`, `object`, `object_curie`, `coverage`, `reviewer`, `review_date`, `status`, `confidence`, `scope`, `expires_at`, `notes`, `import_set_id`, `source_hash`, `modified_at` | Evidence relationship with separate addresses and identities |

The mapping primary key includes `mapping_set_id`, the subject/predicate/modifier/object assertion, and `source_path`. Separate releases and duplicate source occurrences therefore do not overwrite one another. Endpoint indexes cover mapping subjects/objects and junction `subject_curie`/`object_curie`.

### Projection rules (Tier 1 → Tier 2)

1. Read only notes with valid `_crosswalker` provenance; canonical Markdown remains the authority.
2. Project `_crosswalker.import_set.id` to nullable `import_set_id` on concepts, mappings, and junction notes. Legacy unstamped records project `NULL`.
3. Project concept `parent_curie` directly. Never derive it from the `parent` wikilink.
4. Project junction `subject_curie` and `object_curie` directly. Never derive them from wikilink text.
5. Normalize mapping-set identifiers and predicate modifiers through the shared provenance helpers, then store each mapping occurrence with its source path.
6. Reconcile an ontology's displayed version deterministically across projected concepts using binary lexical order, so file traversal order cannot change the result.
7. Exclude `predicate_modifier = 'NOT'` from effective graph edges, including symmetric and inverse expansion. Direct `crosswalkBetween()` queries retain negated rows and their provenance.
8. Invalidate mapping-dependent closure rows and depth-coverage state together whenever mappings change.
9. Prune unseen rows only during a complete `full` projection. Filters, projection errors, or unreadable-but-present frontmatter suppress pruning.

### Schema-version migration

Tier 2 now ships `tier2-sqlite-v4`. Because Tier 2 is derived, opening any other schema version drops and recreates the sidecar, then reprojects canonical Tier 1 Markdown. v4 adds nullable `import_set_id` ownership projection to concepts, mappings, and junction notes. It preserves the v3 mapping-occurrence, negation, endpoint-identity, and depth-safe closure-cache model.

## §8 Cross-schema invariants & constraints

These are the rules the projector and import paths both respect:

1. **Contracts stay distinct:** the Recipe Schema Contract governs ImportRecipe intent; the Tier 1 Schema Contract governs canonical member records.
2. **Tier 1 is canonical local managed authority:** every Tier 2 column has a Tier 1 source. No authoritative managed knowledge lives only in Tier 2.
3. **Knowledge Set is conceptual, not a universal envelope:** ontology, mapping-set, and evidence-set aggregates may be represented through Tier 1 members without one generalized aggregate schema.
4. **Managed ownership is declared:** a producer may update or clear only recipe-declared managed fields and `_crosswalker` provenance. `user_preserve` fields remain untouched.
5. **Identity is not address:** `parent_curie`, `subject_curie`, and `object_curie` are explicit stable identities; wikilinks remain clickable addresses and are never reverse-parsed into identity.
6. **Mandatory junction fields:** `curie`, `subject`, `predicate`, `object`, and `_crosswalker` (source: `spec/tier1.schema.json § $defs.junction_note_frontmatter.required`).
7. **Crosswalk vocabulary and negation are separate:** `predicate_id` has 6 allowed relationship values, while `predicate_modifier` is absent or `NOT` (source: `spec/tier1.schema.json § $defs.crosswalk_edge_frontmatter.properties`).
8. **Mapping occurrences preserve release provenance:** `mapping_set_id` distinguishes published mapping collections; deterministic assertion CURIEs distinguish repeated occurrences without changing concept identity.
9. **Graph traversal uses only positive assertions:** direct queries may return negated assertions, but closure, symmetric expansion, and inverse expansion exclude `NOT`.
10. **Version-governed representations rebuild safely:** ImportRecipe, Tier 1 records, and Tier 2 SQL carry independent versions appropriate to their roles. Tier 2 can be discarded and regenerated.

## §9 Build sequence

The original v0.1 implementation plan decomposed the governing contracts and representations in this order:

1. **`_crosswalker` metadata v2** — extend existing `src/generation/generation-engine.ts` to write the v2 fields. Lowest-risk: this is just a frontmatter shape change.
2. **Junction note 13-field schema** — implement junction-note generation as a new code path in the generation engine. Triggered by ImportRecipe with crosswalks that target evidence documents.
3. **ImportRecipe v2** — refactor `src/types/config.ts` to the v2 shape. Migration script for existing v1 saved configs.
4. **Tier 2 sidecar SQL projector** — new module in `packages/core/`. Auto-runs on vault load. Lazy closure cache + sqlite-vec embedding integration.

Each step has a corresponding test:
- Round-trip test: write Tier 1 frontmatter, project to Tier 2 SQL, query, confirm semantic equivalence to source data.
- Idempotency test: project twice; second projection is a no-op.
- Recovery test: delete the .sqlite, reload, confirm reprojection produces byte-identical state.

## §10 Open sub-decisions (deferred from this spec)

Items flagged in [Ch 07's "remaining open sub-decisions"](/crosswalker/agent-context/zz-log/2026-04-10-evidence-link-edge-model-synthesis/) and elsewhere that this spec does **not** lock in:

1. **UUID enterprise resilience scope** — Ch 09 settled UUIDv7 + sha256 + CURIEs; the *enterprise* scope (cross-tenant ID stability) needs a separate design pass.
2. **Multi-editor conflict resolution** — when two users edit the same junction note simultaneously, what does the merge look like? Out of v0.1 scope; v1.0+ collaboration story.
3. **Legacy inline-field migration script for v0 vaults** — for users who have notes with the superseded `key:: value` syntax. Out of v0.1 scope.
4. **Tested vault scale threshold documentation** — Ch 18 gives a model; need empirical confirmation in real vaults of varying size.
5. **OSCAL ↔ Crosswalker mental-model documentation** — `reference/registry/oscal/` page extension. Listed in roadmap Foundation tasks.
6. **`StewardshipProfile` v2 schema** — separate from this spec but referenced via `ImportRecipe.stewardship_profile_id`. Per the [05-01 commitments log](/crosswalker/agent-context/zz-log/2026-05-01-foundation-commitments-and-followon-research/), the schema design pass is deferred until after v0.1 schemas land.
