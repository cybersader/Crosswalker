## Goal

Make the bundled engine **streaming-by-design** so it can handle source files larger than RAM. Refactor `generateFromRecipe` and `generateNotes` to consume an `AsyncIterable<Row>` instead of requiring an in-memory `ParsedData.rows[]` array. PapaParse's dedicated stream API feeds the async iterator directly with bounded buffering.

This is the implementation of Mode 1 (bundled projector) at scale, per the [2026-05-05 two-mode architecture decision](/crosswalker/agent-context/zz-log/2026-05-05-two-mode-architecture/). Without it, composition with external streaming CSV/JSON producers caps at RAM-sized inputs, defeating the purpose.

## Status

✅ Done (2026-05-05). `ParsedData.rows: Row[] | AsyncIterable<Row>` shipped with full backwards-compat. New `parseCSVFileStream()` returns ParsedData where rows is an AsyncIterable that pulls per-row from PapaParse via the step callback with backpressure (buffer caps at 100 rows). The engine now consumes both sync and async iterables through bounded iterator traversal. 153 tests passing (116 unit + 37 E2E across 8 spec files including new `streaming.spec.ts` with 4 tests covering AsyncIterable consumption + eager-array backwards-compat).

**Status last verified:** 2026-09-05 — scoped to the streaming API and engine boundary at commit `30aee63b`: `ParsedData.rows` still accepts arrays or async iterables, `parseCSVFileStream()` still uses 100/10-row backpressure, and `forEachConcurrent()` consumes sync or async iterators. The 2026-05-05 test counts were not rerun.

**Current limitation:** the wizard's current `>5 MB` branch detects streaming mode but calls `parseCSVFile(..., { streaming: true })`; that function still accumulates every row before returning. Therefore the page's automatic bounded-memory wizard-import claims are not current proof. Wiring the wizard to `parseCSVFileStream()` requires a source change and real-Obsidian verification outside this documentation-only slice.

## Scope

**In:**
- `ParsedData.rows: Row[] | AsyncIterable<Row>` — streaming-friendly union; backwards-compatible with existing array consumers
- `parseCSVStream(file)` — returns `AsyncIterable<Row>` directly via PapaParse step callback piped to async generator (no `results.data[]` accumulation)
- `generateFromRecipe` and `generateNotes` accept either form via `for await` iteration
- E2E test (`tests/e2e/streaming.spec.ts`) — feeds a large synthetic CSV (~1M rows or memory-budget-equivalent), confirms RAM doesn't grow with input size, confirms output Tier 1 vault is correct
- Wizard preview unchanged — still loads first ~50 rows into a small `ParsedData` for preview UX
- Wizard detects sources >5 MB with `shouldUseStreaming()`; binding its generation run to `parseCSVFileStream()` remains open, as noted under Current limitation

**Out:**
- CLI pipe interface (external producer piped into a future Crosswalker CLI) — defer to v0.5+
- XML / RDF streaming parsers — defer to v0.2+
- Web Worker offload of parse — Ch 23 §9.5 says workers are unreliable for this; main-thread cooperative-yield is the v0.1 path
- Programmatic AsyncIterable callers (advanced composition pattern) — exposed via `plugin.runImportFromRecipe` API; doc page on it deferred to v0.2

- [ ] Refactor `generateFromRecipe` (in `src/generation/generation-engine.ts`) — change row loop from `for (let i = 0; i < parsedData.rows.length; i++)` to `for await (const row of asyncRowsOf(rowSource))`; helper `asyncRowsOf` normalizes either array or iterator into AsyncIterable

- [ ] Wizard: detect `shouldUseStreaming(file)`; if yes, use `parseCSVStream` directly without intermediate `ParsedData.rows[]` accumulation

  - E2E (`tests/e2e/streaming.spec.ts`): synthetic 1M-row CSV via streaming path; confirm import succeeds; confirm RAM growth stays bounded; confirm output count matches input row count
