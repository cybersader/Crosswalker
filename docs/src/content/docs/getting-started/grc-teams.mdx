## The evidence mapping problem

Every GRC practitioner knows this pain: you have **evidence** (policies, procedures, audit findings, screenshots, technical configs) scattered across wikis, SharePoint, OneNote, and email. You have **[frameworks](/crosswalker/concepts/framework-standards/)** (NIST, CIS, MITRE, CRI, FFIEC) in massive spreadsheets. And you need to prove to [auditors](/crosswalker/concepts/institutional-landscape/#the-entities) that specific evidence satisfies specific controls.

This is **evidence mapping** — the core work of compliance — and the tools are broken. Understanding [who owns what](/crosswalker/concepts/institutional-landscape/) in the ontology ecosystem helps explain why.

**Built for GRC first; works for any structured framework or taxonomy.** Every example on this page is compliance, and the one-click imports that ship today are all compliance sources. Nothing in the note format is compliance-specific, though, and that works in your favor: the non-GRC structures your team already maintains — vendor questionnaires, internal control taxonomies, asset and service hierarchies, skills matrices — go through the same guided import, so they can live in the same vault and link to the same evidence instead of a separate tool. [Why the core stays domain-neutral](/crosswalker/concepts/what-makes-crosswalker-unique/#5-domain-neutral-core-grc-first-launch-surfaces).

### Two worlds that don't talk to each other

| Framework world (structured) | Evidence world (unstructured) |
|------------------------------|-------------------------------|
| NIST 800-53: 1000+ controls in a spreadsheet | Your MFA policy lives in SharePoint |
| CIS v8: 153 safeguards in an Excel tab | Your firewall configs are in a wiki |
| CRI Profile: Diagnostic statements across 8 sheets | Your audit findings are in email threads |
| ATT&CK: 200+ techniques in a matrix | Your detection rules are in SIEM configs |

The gap between these worlds is where compliance teams spend most of their time — manually searching, cross-referencing, and documenting connections in yet another spreadsheet.

### Why spreadsheets fail at evidence mapping

- **No bidirectional linking** — you can write "AC-2 → MFA Policy" in a cell, but the MFA Policy document doesn't know it's been mapped. Update the evidence and the mapping is instantly stale. This is the [referential integrity gap](/crosswalker/agent-context/constraint-enforcement/#the-referential-integrity-gap) that [file-based systems](/crosswalker/concepts/file-based-graph-database/) face.
- **No metadata about the mapping itself** — Is this evidence *sufficient*? Who *reviewed* it? *When* was it last validated? What *type* of evidence is it? Spreadsheets can't answer these. Crosswalker solves this with [typed links and edge metadata](/crosswalker/agent-context/link-metadata-system/).
- **No cross-framework traceability** — when an auditor asks "show me the CRI diagnostic statement, the CSF subcategory it maps to, the 800-53 control, AND the evidence" — that's a manual detective hunt across 4+ spreadsheets. [Framework crosswalks](/crosswalker/agent-context/framework-crosswalks/) make this one click.
- **No query capability** — you can't ask a spreadsheet "which controls have zero evidence?" without formulas that break when rows shift. [Obsidian Bases](/crosswalker/concepts/metadata-ecosystem/) solves this natively.
- **Sync is impossible** — frameworks update, evidence moves, people leave. The mapping sheet becomes a graveyard of stale references. This is the [ontology evolution](/crosswalker/concepts/ontology-evolution/) problem — and it's [never fully solved](/crosswalker/concepts/operational-landscape/#tier-4-operational-maintenance-ongoing), only managed.

### The multi-framework regulatory pressure

Financial institutions using CRI Profile must simultaneously demonstrate compliance with NIST CSF, FFIEC CAT, CISA CPG, and sometimes NYDFS and SEC requirements. Each regulator uses different terminology for overlapping requirements. Without systematic [crosswalking](/crosswalker/agent-context/framework-crosswalks/), teams map the same evidence to the same concept in 5 different spreadsheets.

This isn't just inefficiency — it's a compliance risk. Inconsistent mappings across frameworks signal to auditors that the organization doesn't truly understand its control environment.

## What Crosswalker does differently

Crosswalker eliminates the gap between frameworks and evidence by putting **everything in one place** — your Obsidian vault — where frameworks, evidence, policies, and notes are all **interlinked and queryable**.

### Import frameworks as navigable knowledge

```
Your Vault
├── Ontologies/                   ← default output folder (change it in settings)
│   ├── NIST-800-53/
│   │   ├── Access Control/
│   │   │   ├── AC-1.md          ← full control text, metadata, crosswalk links
│   │   │   └── AC-2.md          ← linked to CIS 5.2, CIS 6.3, PR.AC-07
│   │   └── ...
│   ├── CIS-Controls-v8/
│   └── MITRE-ATT&CK/
├── Evidence/
│   ├── MFA-Policy.md            ← links directly to AC-2, CIS 6.3, PR.AC-07
│   ├── Firewall-Audit-Q1.md     ← links to SC-7, CIS 4.4, DE.CM-01
│   └── Pen-Test-Report.md       ← links to CA-8, ATT&CK techniques
└── Reports/
    └── Compliance-Dashboard.md   ← live queries across everything
```

Every framework control is a note you can open, read, and link to. No more hunting through spreadsheet rows.

### Map evidence with structured metadata

This is the breakthrough. When you link evidence to a control, you can attach **metadata about the relationship itself** — as a small evidence-link note whose properties describe the relationship:

```yaml
# Evidence Links/MFA-Policy--implements--AC-2.md
---
kind: junction-note
subject: "[[MFA-Policy]]"
predicate: implements
object: "[[AC-2]]"
status: implemented
coverage: full
reviewer: Alice
review_date: 2026-03-15
---
```

A second link from the same policy to `IA-5` can carry `coverage: partial` and a gap note. Because every relationship is a note with plain properties, "show me all controls where evidence is *partial* and needs remediation" is one Bases filter — not a spreadsheet treasure hunt.

### Crosswalk between frameworks automatically

Import NIST 800-53 and CIS Controls, and Crosswalker generates the WikiLinks between corresponding controls. The crosswalk lives in your vault as navigable, queryable connections — not a separate mapping spreadsheet.

When an auditor asks "trace from CRI diagnostic statement through CSF to 800-53 to your evidence" — you follow the links. Each hop is one click.

### Query your compliance posture

Use [Obsidian Bases](/crosswalker/concepts/metadata-ecosystem/) for compliance dashboards:
- "Which controls have **no evidence**?" — filter by backlink count = 0
- "Show all controls where evidence is **insufficient**" — filter by metadata
- "What evidence was **last validated more than 90 days ago**?" — date filter
- "How many controls in each family have evidence?" — group by folder

A dashboard is a plain `.base` file you drop in your vault. Save this as `Reports/Control-Coverage.base` and Obsidian renders three live views over the same control notes:

```yaml
filters:
  and:
    - file.inFolder("Ontologies/NIST-800-53")
    - 'file.ext == "md"'

formulas:
  evidence_count: 'file.backlinks.length'

properties:
  control_id:
    displayName: "Control"
  family_name:
    displayName: "Family"
  last_validated:
    displayName: "Last validated"
  formula.evidence_count:
    displayName: "Evidence count"

views:
  - type: table
    name: "Controls with no evidence"
    filters:
      and:
        - 'file.backlinks.isEmpty()'
    order:
      - control_id
      - title
      - family_name

  - type: table
    name: "Evidence going stale"
    filters:
      and:
        - 'last_validated < (today() - "90d")'
    order:
      - control_id
      - title
      - last_validated

  - type: table
    name: "Coverage by family"
    groupBy:
      property: family_name
      direction: ASC
    order:
      - control_id
      - title
      - formula.evidence_count
    summaries:
      formula.evidence_count: Average
```

Change a filter, get a different report. No formulas to re-drag, no rows to keep in sync.

### Own your data

Every control, every mapping, every piece of evidence metadata is a **plain markdown file** in a folder on your disk. No vendor database. No API dependency. Version control with git. Move between tools freely. Your compliance knowledge base is yours.

### Handle framework updates without panic

When NIST publishes CSF 3.0, re-import alongside 2.0. Your evidence links to 2.0 controls stay intact. Migrate at your own pace using the [version-tagged folder approach](/crosswalker/concepts/framework-versioning/). No more "framework update breaks everything" emergencies.

## Supported frameworks

Crosswalker imports **any structured data** from CSV, XLSX, or JSON. These sources ship with one-click recognized import:

| Framework | What you get |
|-----------|-------------|
| NIST CSF 2.0 | Subcategories in function/category structure (three layout variants, including the CPRT export) |
| NIST SP 800-53 Rev 5 | Controls and enhancements as notes |
| CIS Controls v8 | Controls and safeguards, two layout variants |
| MITRE ATT&CK | Techniques with tactic metadata |
| CRI Profile v2.2 | Diagnostic statements |
| SCF 2026 | Controls from the Secure Controls Framework workbook |
| OLIR-style crosswalk files | Framework-to-framework mapping rows as typed crosswalk notes |

Not on the list? If it's in a CSV, XLSX, or JSON export, Crosswalker imports it through the same guided mapping — it just doesn't get the one-click head start. (The companion Python CLI in the repo additionally batch-imports MITRE D3FEND and ENGAGE.) See [framework data sources](/crosswalker/reference/framework-data-sources/) for technical details.
