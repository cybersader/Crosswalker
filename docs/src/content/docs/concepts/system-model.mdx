<Aside type="tip" title="What this page is">
The **picture-first** overview of the whole system. Every box below links to the page that explores it in depth.

The model is **domain-neutral**: Crosswalker represents an *ontology* — a set of concepts and the typed relationships between them — as canonical, queryable Markdown. Compliance frameworks are the launch use case, not the model; where something is compliance-specific it's flagged as such. For the detailed reference (component-to-tier matrix, read/write flows), continue to [system architecture](/crosswalker/concepts/system-architecture/).
</Aside>

## One glance — source data to answers

Crosswalker turns whatever shape your data ships in into a **canonical Markdown vault**, then makes that vault queryable. Everything else is detail on this spine:

## From source to structure — `render()` + the 5 mechanisms

This is the engine room. **`render()`** is one pure function — `render(Recipe, Concept) → Address` — and it takes the two things people always ask about by name:

- a **[Concept](/crosswalker/concepts/terminology/#concept)** — *one record from your source*. Just a bag of named fields. Below it's a biological species, but it could be a security control, a product, a city — any [ontology](/crosswalker/concepts/terminology/#ontology).
- a **[Recipe](/crosswalker/concepts/terminology/#recipe)** — *your rules*. For each field (or combination of fields), which vault primitive it becomes — folder, file, tag, frontmatter, or link — written as a **template**.

Feed both to `render()` and it hands back a fully-formed note: *where* it lives and *what's written* in it.

**Two kinds of rule are in play.** Most are plain **templates** — `{field}` interpolation with a closed filter set (`{habitat|lower}`, plus `slug · tagsafe · fs-safe · truncate`). But the `folder` rule does more: <code>split(lineage, ";")</code> is a **transformation expression** (**JSONata**) that breaks **one** packed field — `lineage` — into **three parts** (`Mammalia`, `Carnivora`, `Felidae`). Pairing those parts with the `folder` mechanism is what *nests* them into levels — but that pairing is a free choice, which is the whole point of [the next section](#hierarchy-is-a-choice-not-a-default). This is the everyday taxonomy-code case: when a single key packs a hierarchy — a lineage string, a Dewey number, a code like `AC-2` or `DE.AE-02` — an expression splits, slices, or regexes it into parts. Anything past the closed filters (conditionals, lookups, concatenation) escapes the same way.

So `render()` pulled **several fields and used them five different ways at once** — folder depth from *one* split key, the filename from `common_name`, a faceted tag from `habitat`, two frontmatter keys, and a typed `[[wikilink]]` from `family`. **Structure comes from whatever you template *or compute* — not from one magic identifier.** The five primitives a rule can target:

### Hierarchy is a choice, not a default

Look again at what the split did: it produced three **parts** — nothing more. It said nothing about nesting. Whether those parts become a deep folder tree, a flat set of tags, an outline of headings, or a graph of links is decided by the **mechanism** you pair them with. The *same* `[Mammalia, Carnivora, Felidae]` renders four different ways:

Each is a different *shape* of the same hierarchy: **folder** nests on disk (browse it); **tag** is flat and faceted, so one concept can sit under many axes at once (cross-cutting search); **heading** nests inside a single document (one reference page); **wikilink** is parent/child as graph edges with no folders at all (traversal + graph queries).

**How the system makes this possible** — three choices working together:

1. **A closed set of five mechanisms** (`folder · file · heading · tag · wikilink`). Structure can only ever be one of these, so the space is small, total, and predictable — not an open-ended scripting surface.
2. **`render()` is the single coupling point.** The transformation (what a part *is*) and the mechanism (what *shape* it takes) are orthogonal — *(level + mechanism) → address* lives in exactly one function. Swap the mechanism, keep the data, get a different vault; the engine never changes.
3. **`also_emit` runs mechanisms in parallel.** One import can be a folder tree *and* a parallel tag facet at once — folders to browse, tags to slice ([Ranganathan-style faceted classification](/crosswalker/concepts/hierarchy-primitives/)). You're never forced to pick just one.

So **hierarchy is something you declare in a recipe, never something baked into Crosswalker.** Re-point the mechanisms and the same source becomes a tree, a flat tag-space, an outline, or a link graph — that is the control and flexibility the model buys you.

<Aside type="caution" title="Open question — variable-depth structure (under research)">
The diagrams above are **conceptual**. v0.1 renders **fixed / known depth** well: you declare one `layout` row per level (or the wizard derives them from sample delimiters), and the `split` filter returns one part *by index*. What's **not** yet first-class — and is under active research — is **variable / ragged depth**: splitting one packed key into *however many parts there are*, per row, with smart fallback when a regex over- or under-splits — plus polyhierarchical **tag** layout, data-driven **heading** depth, and hierarchy-as-**graph-edges**. Honest current-state + the design space: [open-question log](/crosswalker/agent-context/zz-log/2026-06-14-variable-depth-hierarchy-open-question/) → [Challenge 42](/crosswalker/agent-context/zz-challenges/42-variable-depth-hierarchy-generation/).
</Aside>

## The ingest tools — readers by source shape

A reader is a *front-end* to `render()`, never a new engine — and the same readers back the wizard's parsers (*one reader, two doors*). There's one per shape structured data actually arrives in, and together they produce the two things any vault holds: **concepts** (the nodes) and **relationships** (the typed edges between them):

| Source shape | What a reader does | Produces |
|---|---|---|
| **Flat table** — rows in a CSV or spreadsheet | one row → one concept | concept notes |
| **Nested document** — records inside a tree (JSON, at an iterator path) | one record → one concept | concept notes |
| **Mapping table** — one source id against many target ids | each pair → one typed edge | relationship (crosswalk) notes |

The *shapes* are general. The current named implementations in `tools/` — `generate-fixtures` plus the `crosswalk-from-*` extractors — happen to target the compliance launch corpus; see the [ingestion dev log](/crosswalker/agent-context/zz-log/2026-06-02-ingestion-tooling-dev/) for those specifics and the [readiness board](/crosswalker/agent-context/zz-log/2026-06-12-urm-ingestion-readiness/) for status.
